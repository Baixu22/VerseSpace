# Workbench 定位：任务主权层（v3，取代两态模型）

- 状态：已接受
- 日期：2026-08-29
- 演进：v1「任务赢过会话」（单边，已废）→ v2「两态模型」（半修正：承认对话是探索态的最优界面）→ **v3 本文**：交互层不再有争议，产品定义落在「任务的身份证 + 会话的归属权 + 治理的副产品化」。

## 一、裁定：什么是真问题，什么是无病呻吟

- 无病呻吟：试图推翻对话式交互（塔台取代对话、手动契约、Dify 式工作流 DAG）。对话是 LLM 的终端交互，范畴错误。
- 真问题：**会话没有身份证**。当并行线程数超过人的注意力且任务跨天时，会话列表没有任何治理能力——不知道哪个会话动了哪些文件、哪个还在跑、哪个做完了、哪些冲突。agent 越强，失效越重。

## 二、产品定义（三句话）

1. **每个任务一张身份证**，创建于对话之前或之始：ID、元数据（动过的文件、跑过的命令、做过的决定、验证状态）、履历（事件）、场所（worktree / 分支）。
2. **会话挂靠任务之下**：一个任务可有多段会话（探索 / 实现 / 复查）；会话无主流离是治理失效的根源。
3. **治理即副产品**：身份证随对话自动生长（git diff、transcript 解析、验证结果），不由用户前置填写。设计时税由此消失。

非目标：不做 a2a / multi-agent 互聊协议（人始终是唯一对话者与裁决者）；不做取代对话的工作台；不做手动工作流编排。

## 三、与引擎的分工

Claude Code 式对话 agent 是正确的引擎，Workbench 不做更好的对话，做让对话有归属的壳：
`Claude Code 卖引擎，Workbench 卖任务身份证 + 行驶记录仪 + 登记系统。`
交互层沿用对话式 agent，无创新亦无需创新——创新全部在沉淀层。

## 四、对既有 MVP 的对账

- 保留：goal / workspot / checkpoint / Verifier / 事件流 / 接口锚定（= 身份证的本体、场所、印章、履历）；agent runner（履约态特例）。
- 降级：塔台 GUI → 身份证的可选视图（渐进披露，无例外时隐形）。
- 废弃：手动契约、capture 式事后结晶（被运行时自动生长取代）。
- 缺口（下一个功能）：会话与任务的绑定层——`workbench task new` / `task talk`（包裹 CLI、transcript 落盘、元数据自动上卡）。

## 五、一句话

**我们不做更好的对话，也不做取代对话的工作台；我们做对话的户籍系统——每个任务有身份，每段会话有归属，治理是副产品而非前置作业。**
