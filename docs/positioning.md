# Workbench 定位：两态模型（取代「任务赢过会话」的单边论述）

- 状态：已接受
- 日期：2026-08-29
- 缘起：对 v0.3 交互策略总结的用户反驳（要点：总成本账只算监督税没算设计税、概念负载被低估、对会话的批判部分是稻草人、复杂性只是搬家）。反驳成立，本文是修正后的正式定位。

## 一、两个工作态，各有最优界面

| | **探索态** | **履约态** |
|---|---|---|
| 特征 | 目标未知、单线程、短周期、答案靠迭代发现 | 目标已结晶、多路并行、长周期、产出可机器判定 |
| 最优界面 | 对话（零启动成本，迭代即发现） | 契约（机器验证、worktree 隔离、例外管理） |
| 信息税 | 迭代成本（低且自然） | 启动税（高）+ 监督税（低）+ 维护税（中） |

结论：**不存在普遍赢家。** 契约制只在 `并行路数 × 任务时长 × 重做频率` 越过阈值后划算；对日常的「问一句 → 看结果 → 微调」型交互，对话是更好的界面。

## 二、产品命题：边界转换才是价值所在

会话是勘探，契约是开采；勘探的产出物之一就是契约本身（验收条件在对话迭代中被经验性地发现）。Workbench 的定位据此收窄为：

1. **升格（对话 → 契约）**：对话验真后，把验收条件、改动文件、worktree 固化为工位跑道，对话原文留作证据流。
2. **降格（契约 → 对话）**：跑道中发现任务是探索性的，就地拆回对话。

即：**已结晶工作的执行层 + 结晶那一刻的捕捉器。** 探索态的界面永远是对话（住在 Helmor / Claude Code 等工具里），Workbench 不与之竞争。

## 三、认知负载：渐进披露

默认用户只需三个概念（goal / workspot / checkpoint），且都由升格动作自动产生。DAG、接口锚定、Automaton 是系统内部机制，不是用户必修课。塔台在无例外、无多跑道时应保持隐形。

## 四、不变的内核

反驳确认了三个独立成立的洞察，它们是 Workbench 剩余的存在理由：

1. 「完成」由机器裁决（exit code），不由模型自述；
2. 状态外置于文件系统（git 可追踪、工具无关、崩溃可恢复）；
3. 上下文按需编译（对抗 context rot）。

它们的重量对 5% 的履约态场景是恰到好处的——而 Workbench 只为这 5% 服务，并负责把工作从对话里结晶进来。
