# 地标投影修复提案（TF-0161）

> 触发证据（2026-09-12）：自审在唯一有地标的现场把 3 条**全部驳回**；另外三个现场
> **一条文件级地标都出不来**（阈值口径），自审无从累积。

## 1. 现状（可复现的两条事实）

1. **空集**：node-verified / LHA3I4 / VAKSgQ 三个现场，阈值口径（DOI>10）的文件级
   地标集合都是空的——`landmark-review-queue.ts` 对三者的输出都是「地标 0 条，无样本」。
   相对选择（每会话 top-K）在同一批现场是 100% 覆盖，但那不是现在的 L1 分母（TF-0159）。
2. **打偏**：唯一有地标的租户上，3 条被自审全部驳回。证据取自黑板：`git-main` 在
   `src/alpha.ts`、`src/beta.ts` 上各 25 次**同种** `edit`，`editor-1` 在 `src/beta.ts`
   上 25 次 `selection`；三者会话 **0 声明产物**、无活动记录、其它 handle 零触碰。

也就是说：越线靠的是**同一手势重复计数**，不是工作重要性。自审读数 0/3 与空集是
同一个病：投影把「重复」当成了「核心」。

## 2. 三个候选与取舍

| 候选 | 做法 | 打中什么 | 风险 |
| --- | --- | --- | --- |
| A 同种手势去重 | 窗口内同 handle 同 kind 只算一次 | 膨胀最直接 | **误杀真实信号**：反复编辑同一文件在 Mylyn 模型里本来就是兴趣证据，不能一刀切 |
| B 递减收益上限 | 同 handle 同 kind 的第 n 次贡献按 log 或封顶（例如 3 次后每次只加 0.2） | 保留「反复编辑=强信号」，抑制 25 次刷分 | 阈值需重标定，可能整体下移 |
| C 来源门 | 地标必须来自声明过产物/活动的会话（`generated`/`used` 非空） | fixture 噪声最精准 | CLI 未声明时会漏掉真工作，单独用会把整片现场判死 |

**推荐：B 为主，C 只在极端形状上否决**——即「零声明产物 + 只有一个 handle + 只有一种
手势」三者同时成立时才否掉。这样 fixture 噪声被清掉，真实重复编辑（有产物声明、
或多文件多手势）不受影响。

> **2026-09-12 实测后修订（推翻上面这条推荐）**：B 已实现为默认关闭的 `repeatCap`
> 参数并量过，结论是**它修不了这个问题**，见下节。推荐改为 **C 为主**。

## 2b. 实测结果（决定取舍）

| 测量 | 出厂 | 候选 B（free=3, after=0.2） |
| --- | --- | --- |
| 租户：阈值口径文件级地标 | 3 条（+2 条容器，占比 40%） | **0 条**（+0 容器） |
| 其余三现场：阈值口径文件级地标 | 0 条 | 0 条（不变） |
| 租户：相对选择（每会话 top-3） | 89 会话 / 10 个文件 | **逐字相同**（89 / 10） |
| 其余三现场：相对选择 | 32/15/12 会话 · 4/10/10 文件 | **逐字相同** |

三条结论：

1. **B 能清掉膨胀，但不能让空集长出地标**——三个现场改前改后都是 0 条；租户甚至从
   「3 条错的地标」变成「0 条」，L1 在那里直接变成不可计算。
2. **B 对相对选择毫无影响**：排名逐字不变。原因很直白——`git-main`/`editor-1` 这类会话
   **只碰过一个文件**，怎么折减它都还是那个会话的第一名。**这不是权重问题。**
3. 真正的问题是**这类会话没有工作**：0 声明产物、无活动记录、单一 handle。所以答案
   在候选 **C（来源门）**，而不是在权重上做文章。

**修订后的推荐**：先按 **C** 把「零声明产物 + 单 handle + 单种类」的会话排除出候选
（它们不是"核心选错了"，是"根本没有工作可谈"），再看阈值/分母（TF-0159）。`repeatCap`
保留为**默认关闭的诊断项**：它能把"纯重复越线"这条独立病灶量出来，但不作为修复。

## 2c. 按会话种类分组（决定性的那一刀）

把四个现成现场按**会话种类**分组重算，结果一致到不需要解释：

| 现场 | `agent`（干活的会话） | `agent` 阈值地标 | `git`（文件监视） | `git` 阈值地标 |
| --- | --- | --- | --- | --- |
| live-tenant | 83 会话 / 415 次触碰 | **0 条** | 1 会话 / 50 次 | **2 文件 + 2 容器** |
| node-verified | 30 / 140 | **0 条** | 1 / 20 | **2 + 2** |
| LHA3I4 | 13 / 40 | 0 条 | 1 / 2 | 0 条 |
| VAKSgQ | 10 / 38 | 0 条 | 1 / 2 | 0 条 |

**每一个文件级地标都来自 `git` 监视会话**（tenant 3/3、node-verified 2/2），剩下 1 条来自
`human` 编辑器会话；83 个 `agent` 会话、415 次真实触碰，**一条都出不来**。

原因不神秘：DOI 是**按会话**算的，`git` 监视会话的全部工作就是在少数文件上反复落笔
（50 次 × 编辑权重 2 集中在 2 个文件 → 轻松过 10 分线），而 `agent` 会话的触碰是**分散**的
（多文件、每种手势几次 → 每条都过不了线）。于是阈值口径实际量的是「**谁把某个文件夯得最狠**」，
而夯得最狠的恰恰是那个**不干活的记录者**。

这也解释了上两节的全部现象：为什么自审 3/3 驳回（集合就是"git 看到了什么"）、为什么
B 修不动（改权重不改变"谁夯得最狠"）、为什么 C 的产物判据不可用（**这些现场里没有任何会话
声明过产物**，84/84 都是 0，判据没有区分度）。

**修订后的推荐（按优先级）**：

1. **候选 D·种类门（必做）**：记录型会话（`git` 监视、`human` 编辑器）不参与地标候选——
   它们记录的是"文件被动过"，不是"这次干活的核心"。依据就是上表：它们贡献了 100% 的
   文件级地标，却只占极小比例的触碰。
2. **候选 E·会话内证据形状**：同一 handle 上同种手势的极端重复（B）保留为**诊断**——它能
   指出"这条地标靠重复越线"，但不作为修复手段。
3. 种类门之后再谈阈值与分母（TF-0159）：先让候选集合里只剩真干活的会话，再决定用什么尺子量。
   顺序反了就会像 B 那样——把尺子改得很精细，量的还是同一批错东西。

## 3. 验收（修好的判据，按顺序验）

1. **不再空集**：四个现场里至少三个能产出非空的**文件级**地标集合（现在 1/4）。
2. **不再打偏**：租户复跑自审，认可率从 0/3 抬到 **≥2/3**；被驳回的那三条心跳地标
   必须移出集合或显著降权（可逐条核对）。
3. **不误杀真信号**：构造一个「真实重复编辑 + 有声明产物」的会话，它仍要产出地标
   ——这条是防止为了清噪声把真信号一起杀掉的回归门。
4. **文档同步**：§11 与账本口径、监控告警文案同步更新；负结论（哪种候选被否、为什么）
   留在文档里，不删。

## 5. 与 TF-0159 的关系

TF-0159 换分母（相对选择）能让读数算出来，但**不解决打偏**：top-K 只会把同样的心跳
噪声排到前面。所以顺序是 **先修投影（本节点），再换分母（TF-0159）**——否则换个尺子
量到的还是同一批错东西。
