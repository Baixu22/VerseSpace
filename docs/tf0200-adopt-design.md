# TF-0200 Adopt(收养)设计

## 定位

Adopt 是一次**身份迁移**,而非内容搬运。子线程被提升为主线程,原主线程(源线程)就地归档:它依旧可见、可检索,并且这次收养随时可以反转,恢复到收养前的身份状态。收养只改"谁是主线程"这个身份指针,任何一方的消息内容都不动。

## 需求与边界

1. **改身份不改内容**:收养只切换主/子线程的身份指针,双方消息一字不改、不迁移、不合并。
2. **快照可逆**:收养前对身份状态打快照,支持一次性反转恢复,源线程与子线程各归原位。
3. **源线程自锚点后消息不并入**:以收养时刻为锚点,源线程在锚点之后新增的消息不并入新主线程,只留在已归档的源线程内。
4. **一次手势完成**:收养是单次原子手势(提升 + 归档 + 打快照同批完成),不留中间态,失败即整体回滚。
5. **日志 `thread.adoption_reverted`**:反转操作发出 `thread.adoption_reverted` 事件落日志,记录被恢复的源/子线程身份,供审计与回溯。

## 快照可逆语义

1. **快照粒度**:快照只记身份指针(谁是主线程、源/子线程 id 及各自归档状态),不含任何消息内容或锚点副本——锚点本身也只是一个消息 id 引用。这让快照恒为常数大小,反转成本与线程消息量无关。
2. **adopt/revert 原子性**:adopt 的"提升 + 归档 + 打快照"与 revert 的"恢复指针 + 解档 + 消费快照"各自是单事务,要么全成要么整体回滚,过程中不暴露半收养的中间态。
3. **并发 adopt 竞态**:两个 adopt 若同时以同一线程为源(或目标),朴素实现会让后写者覆盖前写者的快照,反转时恢复到错误身份。建议二选一:
   - **单写者队列**:所有 adopt/revert 手势串行经过一个 per-forest 写者队列,天然排他,实现简单;
   - **版本号 CAS**:身份指针带 version,adopt 时校验并递增(compare-and-swap),版本不符即拒绝并要求调用方重读,吞吐更高但需处理重试。
   小规模下优先单写者队列;若 adopt 成为热点再引入 CAS。

## 恢复面呈现

adopt 后源线程与分支线程在恢复卡/侧栏遵循以下呈现规则:

1. **分支线程(新主线程)**:以主线程身份正常出现在侧栏与恢复卡列表顶部,不带归档标记,承接后续会话。
2. **源线程(已归档)**:侧栏保留其条目但标为「已归档」,置于归档分组内,可检索、可点开,不参与默认活跃列表。
3. **锚点后消息提示**:源线程恢复卡上附「已归档·自锚点后 N 条不在此线程」一行摘要,N 为锚点之后仅留在源线程、未并入新主线程的消息数;N 为 0 时仍显示「已归档」但省略计数。
4. **反转呈现**:一旦 revert,源线程去掉「已归档」标记复归主线程,分支线程降回子线程条目,恢复卡摘要同步撤下。

## 事件与日志

adopt 与 revert 各发一个事件落日志,payload 字段清单如下:

1. **`thread.adopted`**:
   - `forestId` / `newMainThreadId`(被提升的子线程)/ `sourceThreadId`(就地归档的原主线程);
   - `anchorMessageId`(锚点消息 id,界定源线程哪些消息不并入)/ `snapshotVersion`(身份指针版本,供 CAS 与反转定位快照);
   - `refs`:溯源引用,须回指触发本次收养的手势来源(会话 id / 请求 id),使事件可追回到"谁在何时发起"。
2. **`thread.adoption_reverted`**:
   - `forestId` / `restoredMainThreadId`(恢复的源线程)/ `revertedThreadId`(被降回子线程);
   - `snapshotVersion`(所消费的快照版本);
   - `refs`:同样要求回指触发反转的手势来源,与对应 `thread.adopted` 事件形成审计链。

**白名单注意事项**:两个事件均为新增类型,须先登记进事件白名单方可投递,否则被拦截丢弃;`refs` 字段的溯源来源也须在白名单内,禁止把未登记的自由字段塞进 payload。
