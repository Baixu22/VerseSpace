**结论：值得继续做，但不建议继续扩大“多 Agent 工作台”的横向功能。更值得投入的是“已有 Agent 工作在代码变化和交接之后，如何重新获得有范围、有版本依据的可用性”。** 当前最明显的断点不是没有发现文件变化，而是发现之后，受影响的产物、处理动作、验证结果和下一次交接没有接成同一条证据链。

这不是一个无人竞争的新概念。本轮发现的 **Stalegreen、FreshCtx、Proof-or-Stop**，比上一轮主要对照的看板、任务图和消息工具更直接。单独做“测试回执”“依赖图”“行动前 freshness check”，都不足以建立护城河。推荐在现有账本上做一个边界清楚的纵向功能：**可重验交接包——识别哪些既有工作受到变化影响，给出定向修补/重验材料，并让检查结果绑定到实际代码状态。**

本报告是研究与方案评估，不是实施授权或产品验收。未修改产品源码、既有测试、README、声明注册表或任务森林；新增本报告及可复算探针附件。没有提交、推送、发版、发布新 issue 或调用编码模型。

## 3. 当前实现中的关键短板

### 3.1 多段读取被压成最后一段：有记录也会丢覆盖

**场景：** Agent 先读一个文件的接口定义，再读该文件后面的实现；另一个写者只改变前面接口。旧接口仍可能影响当前工作，但读集只保留后一次读取范围。

**本轮实测：** 对同一文件先记录第 1–2 行，再记录第 9–10 行；只改第 1 行。双读取写者收到 **0** 条通知，只读第一段的对照写者收到 **1** 条；真实 `git diff` 可用。不是大文件上限、没有快照或子进程失败造成。

原因是 [session-view.ts:16–36](../../packages/workbench/src/blackboard/session-view.ts#L16-L36) 按路径反复 `reads.set`；后一次覆盖先前的 `span`。后续 [premises.ts:117–121](../../packages/workbench/src/runtime/premises.ts#L117-L121) 按剩下的跨度过滤。

**定性：已实测的有损模型短板。** 当前 API 明说“最后观察”，因此不简单归为函数违背契约；但它低于用户对“记住读过哪些代码”的自然预期。下一轮需要版本化读取片段集合与明确的淘汰语义，而不是只提高哈希上限。不同版本的片段不能无条件并成“最新全文已读”。

### 3.2 通知生命周期与前提有效性耦合：送达不该等于解决

**场景 A：** 模型收到通知、完成一个回合，但并未重新核对依赖。通知已消费不等于旧依据失效问题已解决。

**场景 B：** 模型已经重新读到新文件，但通知尚未确认。继续因旧通知阻断它，会制造不必要的循环。

**本轮实测同时看到两边：**

| 操作 | 实际结果 |
| --- | --- |
| 对一个仍持有旧版本的写者记录成功投递 | pending 变 0，按 pending 输入的同路径 seal 放行；读集仍是旧版本 |
| 之后再次 reconcile | 0 条新通知，已有失效键去重 |
| 另一写者先重读最新版本、不确认通知 | pending 中旧 claim 仍使同路径 seal 阻断 |

这是受控 `deliver` 回调/账本实验，**不是让真实模型故意忽略通知的实验**。

代码依据：[delivery.ts:85–153](../../packages/workbench/src/runtime/delivery.ts#L85-L153) 用已送达身份过滤待发；[premises.ts:135–137](../../packages/workbench/src/runtime/premises.ts#L135-L137) 对旧失效键去重；[seal.ts:95–124](../../packages/workbench/src/runtime/seal.ts#L95-L124) 只消费传入 claims。当前 Claude/Codex 入口给它 pending claims。

**定性：已实测的架构边界，而不只是 #45 的错误确认 bug。** #45 修的是“失败不能称送达”；缺少的是独立的“前提/产物待重验”对象。运输状态可以完成，有效性仍保持待核实。

### 3.3 checkpoint 可携带过期绿灯继续推进

**场景：** 测试通过，Agent 随后又改了实现；接着两轮 `sync` 把 checkpoint 标为 applied、目标标为 done。旧测试并不覆盖新改动。

**本轮实测：** 在隔离工作区运行真实检查子进程，首次通过；把被测文件改坏后继续 `runOnce`，结果为：

- checkpoint：`applied`；归档结果：`passed`；goal：`done`。
- 两轮推进没有重新验证。
- 对相同检查命令独立重跑：`failed`。

场景未声明接口锚；不否认已经存在的接口漂移保护。

代码依据：[verify-checkpoint.ts:50–61](../../packages/workbench/src/runtime/verify-checkpoint.ts#L50-L61) 归档状态/失败输出/时间；[checkpoint-machine.ts:51–59](../../packages/workbench/src/automaton/checkpoint-machine.ts#L51-L59) 推进已验证项；[goal-machine.ts:131–141](../../packages/workbench/src/automaton/goal-machine.ts#L131-L141) 按 applied 完成目标；[goal-validity.ts:9–21](../../packages/workbench/src/automaton/goal-validity.ts#L9-L21) 当前完成失效主要检查接口版本。

**定性：已实测的结果时效性短板。** 已验证是历史事实，当前有效应另算。需要代码/验证命令/作用范围绑定的验证记录，而不是把所有历史 checkpoint 重写成失败。

此外，[verifier/index.ts:131–144](../../packages/workbench/src/verifier/index.ts#L131-L144) 主要判断退出码；成功结果没有保留测试数、实际发现的用例集合或完整作用范围。不能把一个 exit 0 命令自动解释成“全部验收已过”。

### 3.4 `repaired 已修补` 实际是行为代理指标

当前 [notice-window.ts:132–181](../../packages/workbench/src/runtime/notice-window.ts#L132-L181) 主要看受影响路径是否被重读/再写。只有重读、没有任何验证也会归入 repaired；路径匹配不检查“重读版本是否等于通知要求的新版本”。

**本轮纯函数探针：** 构造只有同路径读取的事件，即使版本标签为旧值、0 次验证，结果仍为 `repaired`。[stats.ts:139](../../packages/workbench/src/commands/stats.ts#L139) 输出标签为“已修补”。

**定性：指标语义过强。** 这不否认“发生了后续反应”有用，但它不能成为护城河的正确率或修复率。应区分：收到、重读、观察到新版本、修改产物、程序验证通过。真正不需要改代码的情况也应有独立处理结论，不能被迫产生无意义改动。

### 3.5 最核心的跨文件场景，当前只能部分提示，不能完整归责

**场景：** 读 `api.ts@v1`，据此编写 `consumer.ts`；人把 API 改为 v2。两个文件不重叠，Git 不一定冲突。

[seal.ts:81–86、122](../../packages/workbench/src/runtime/seal.ts#L81-L86) 按路径重叠。探针确认失效 `api.ts` 不阻断 `consumer.ts`。这与 README 的边界一致，**不是新发现一个宣称已解决的 bug**。

真正缺的对象是“这个消费者改动/评审结论/测试结果，基于哪些记录过的输入”。当前 footprint 的读写共现和先后关系不能直接冒充这种因果关系；模型可能使用隐含知识，也可能读过但没有用。

这正是推荐扩展的研究问题：**在不掌控模型推理、不要求改造所有工具的情况下，怎样以明确分级的来源证据，构建足够便宜且有用的影响关系？**

### 3.6 “恢复聊天”与“恢复正确执行上下文”仍是两件事

- 当前聊天子进程在项目根目录启动：[claude-session.ts:106–110](../../packages/workbench/src/chat/claude-session.ts#L106-L110)；批处理有独立 worktree 路径：[agents/capture.ts:84–88](../../packages/workbench/src/agents/capture.ts#L84-L88)。
- 面板单次运行由一个 `runningThreadId` 控制：[send-slice.ts:15–18](../../apps/workbench-ui/src/chat/send-slice.ts#L15-L18)。这不是一个已完成的多工位同时施工 UI。
- `adoptThread` 是线程身份迁移和归档，不是代码合并或验证：[thread-promotion.ts:66–113](../../packages/workbench/src/chat/thread-promotion.ts#L66-L113)。
- 恢复卡已经提供真实读集覆盖说明：[coverage.ts:49–68](../../packages/workbench/src/chat/resume-card/coverage.ts#L49-L68)。不应说项目“完全没有 unknown/覆盖率”。缺的是从卡片发现问题到正确根目录下重验和确认结果的路径。

**更深的跨 worktree 问题：** A 工位的文件仍是它读到的 v1，主线已是 v2；仅比较 A 的磁盘会正确地得出“这里没变”，却答不了“这份成果能否用于现在的主线”。需要同时保留**观察位置**和**预期使用基线**，不能把两个 worktree 的相同相对路径混成一个对象。

### 3.7 覆盖与容量仍有限，但不建议追求无所不见

源码核对的限制包括：2 MB 以上仅比较大小、同尺寸改写仍漏；目录检索不能代表各文件都被读取；可比范围受工具路径形状影响；活跃检测默认 30 分钟；快照至多 64 KB、每写者 20 份；消息到下一用户回合才送达；哈希、范围与快照采集不与 CLI 的实际读取形成原子操作。

它们的含义不同：**size-only、精确 hash、无法测量不能只被折成“可比较/不可比较”两个宣传口径。** 用户需要知道结论依据强弱，但不必收到四级风险告警。

事件查询和 footprint 折叠仍经常读取整份日志：[events.ts:37–70、172–189](../../packages/workbench/src/blackboard/events.ts#L37-L70)、[sessions.ts:35–61、217–224](../../packages/workbench/src/blackboard/sessions.ts#L35-L61)。这是一条可见扩展成本，**本轮没有长周期性能实测，不能宣称目前已发生容量故障**。先测，再做可重建的增量投影，不因为有 JSONL 就先换数据库。

## 4. 外部真实场景：什么值得解，什么只是看起来重要

### 4.1 旧会话继续使用旧规范，而用户以为“恢复”就是恢复到现在

[Claude Code #97722](https://github.com/anthropics/claude-code/issues/97722) 是 2026-09-28 的用户报告，本轮回读仍 open。报告指出进程内 `/resume` 与重新启动 CLI 对 `CLAUDE.md`/记忆索引的刷新不同；变化通知有时含 diff，有时只建议重新读，旧副本仍留在上下文。

**对 Workbench 的启发：** 原生工具已经会发某些文件变化提示，所以“会通知文件变了”本身不独占。可以深入的是“旧任务结论现在依赖什么、哪些结论要撤回或重验”，并在保留历史的同时给出明确当前投影。

这是可核对的第三方复现描述，不是本轮验证了该 CLI 缺陷，更不代表所有版本都有这个问题。

### 4.2 工作区身份丢失，比摘要写得不好更危险

[Codex #27554](https://github.com/openai/codex/issues/27554) 报告 compact 后离开原 worktree、回到主仓库，仍 open。[#20879](https://github.com/openai/codex/issues/20879) 报告原生 `apply_patch` 缺少调用级 workdir，使 hook 难以识别真实目标工位，仍 open。相关 [#25958](https://github.com/openai/codex/issues/25958) 是 **closed / duplicate**，不能写成“已修复”。

**启发：** 交接对象必须包含 repo/worktree/root/base 和工具覆盖状态。只给“更好的摘要”或者复制聊天记录，不能建立执行上下文的连续性。

### 4.3 并发的难点是耦合和集成，不是进程数

[Claude 官方团队文档](https://code.claude.com/docs/en/agent-teams) 已提供共享任务、任务依赖、消息和 `TaskCompleted` 质量 hook；也明确同文件编辑会覆盖、依赖重的工作不适合组队、恢复不会恢复 in-process 队友。

[Cursor 的大规模 Agent 实验](https://cursor.com/blog/scaling-agents) 记录了锁竞争、无层级时避难就易、角色分工带来的改善；同时说专门 integrator 曾制造更多瓶颈，系统需要适度而非无限结构。**不能从它推导“加一个中央集成人就一定更好”。**

[CooperBench v2](https://arxiv.org/abs/2601.13295v2) 在 600 多个协作编码任务中研究协调失败；作者报告其设定下合作成功率平均低约 30%。这支持“独立正确不等于合作正确”，不证明并发总是差，也不是 Workbench 的性能结果。

**启发：** 面向一个人、一个 Agent 和会变化的代码，就已经有足够具体的问题。无需把价值建立在十几个 Agent 同时运行上。

### 4.4 文件隔离不等于运行环境隔离

[Upsun 的 worktree 文章](https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents) 列出端口、依赖安装、数据库、缓存和集成摩擦。它是厂商文章，包含推销自身预览环境的立场；其中“没有工具提前告警”等绝对判断不能采信，本轮已发现反例。

**启发：** 验证记录需要声明非代码输入的范围；但搭建容器云、数据库隔离平台不是当前项目最好的扩展。先支持选定的非敏感配置/lockfile/工具链指纹，外部可变服务未知就写 unknown。

### 4.5 最后一次测试并不等于当前代码已经验证

[Stalegreen](https://github.com/pavangupta352/stalegreen) 把“测试后继续改代码”和“Shell 吞掉退出码”作为主要问题，提供作者自己日志上的回放数据。数据属于单作者自述，不当行业发生率；但可执行机制和本轮 Workbench 隔离反例都说明这个问题具体、可测。

**启发：** 真正让评审者少做事的，不是再附一段模型总结，而是告诉他“哪些检查覆盖了此刻这份改动，哪些已经过期”。

## 5. 必须直面的竞争：不能再靠外围比较得出独占性

下表能力限于本轮读取的来源；“未见”不等于证明整个产品不存在。竞品没有做安装/运行评测。

| 对照方向 | 本轮核实的已有能力 | Workbench 应得出的结论 |
| --- | --- | --- |
| 原生 Claude 团队 / Cursor 编排 | 任务、消息、并行、质量 hook、角色分工 | 多模型、DAG、worktree 和看板不是主要护城河 |
| MCP Agent Mail | 消息、身份、advisory 文件预约、可选 pre-commit guard | “其他工具都等 merge 才发现”不成立；写意图协调已有方案 |
| AgentFS | copy-on-write、文件操作审计、便携状态 | 文件日志/隔离不是独占，且其完整中介路线比旁路捕获更强；不能照搬为当前保证 |
| Entire / Git AI | 会话关联提交、恢复、逐行 agent/model/prompt 归因 | “记得代码怎么写出来”已拥挤；应回答“当时的依据现在还成立吗” |
| Stalegreen | 验证回执、工作树 fingerprint、声明新鲜度门、失败遮蔽识别 | 单独做“别谎报测试通过”不会构成护城河；可以做必要基础，不能把它当终局 |
| Hyperwise FreshCtx | 声明式依赖图、行动前重验、多数据源、框架 wrapper、A2A 收据 | 与“前提守护”直接重合，不是外围工具；写者中立/本地优先也不是独占 |
| Felipe Basurto FreshCtx | 对发送请求的副本替换旧读取、保留历史、预算化当前代码 | 上下文时效性也已有源码级路线；需要特定宿主桥接，不能视为通用能力 |
| Planfence | 计划携带输入版本链接、交接后还原依赖边界、行动前验证与有限重规划 | 依赖溯源不是新算法；应用要提供范围和真实链接，检查不原子绑定副作用 |
| Proof-or-Stop | 新鲜、代码状态绑定的证据驱动生命周期门 | “有证据才能 done”已有直接研究；组织主页本轮仍说明实现待公开，不冒称已运行其开源引擎 |
| TDAD / codegraph-impact | 源码—测试依赖与改动影响分析 | 静态依赖图/建议相关测试也不能单独当创新；可作为范围推导输入 |

### 最值得保留的竞争差别

这几类产品的典型起点不同：

- Entire / Git AI：这段代码是谁、在什么会话里写的？
- Stalegreen：这句“通过了”有新鲜的验证记录吗？
- FreshCtx / Planfence：这次已被应用声明依赖的行动，其依据变了吗？
- **推荐给 Workbench 的起点：我现在接手一份已有工作，期间别人动过仓库；哪些成果还可复用，哪些只需要局部重验，证据和缺口分别是什么？**

这不是“只有我们能做”的事实，而是**适合现有资产、仍有工程难度的产品切口**。同类项目完全可能延伸过来。防御力必须来自低接入成本、可回放失败集、覆盖语义和连续使用中积累的有效材料，而不是命名。

### 论文给设计的两个反例

1. [The Working Set of a Coding Agent](https://arxiv.org/abs/2608.16630v1) 提醒：未读取不等于未依赖；参数记忆和推测可能直接产生错误输出。因此不能把 `read-set` 改个名字就称“真实推理依赖图”。
2. [Planfence v2](https://arxiv.org/abs/2609.03340v2) 明确区分当前观察与计划推导输入。作者的较新分析还说明：输入先刷新，主动作也可能修对，但下游审计者仍可沿旧依据撤销它。**失效与重验需要跨产物传播，不只喂给一个当前模型。** 其原文同时承认声明范围、单模型族、受控修订和检查—副作用非原子等限制。

[Proof-or-Stop v1](https://arxiv.org/abs/2607.14890v1) 也把 proof 定义为信任模型下可准入的证据，不是程序语义正确性。新的 Workbench 设计应该沿用这类边界纪律，而不是承诺“可证明正确”。

## 6. 推荐的完整功能：可重验交接包

### 6.1 面向谁、何时打开

**首要对象：** 已有 Claude/Codex 使用习惯的个人开发者或小型协作环境；维护一个有本地测试、分支和日常改动的仓库，经常跨天继续、换会话、合入其他人的变更。

**最强触发：** 恢复旧任务、切换到新基线、提交前确认、接手另一个 agent 的工作。不是“所有人每次发消息前都填一次任务表”。

**一句话价值：** 不要求你重做整段工作，也不要求你相信旧总结；给你一份当前仍可复用的成果清单，以及必须重新核实的最小责任范围。

这是产品假设，不是已证市场需求或付费意愿。

### 6.2 用户能完成的全流程

1. **正常工作，不新增首条消息仪式。** 对已监督会话、显式登记的写者和已有工位，采集其来源、输出与检查事实。未接入通道继续如实标未知。
2. **在自然边界生成交接包。** 记录产物版本、来源证据、验证记录和执行位置；不要求把隐藏推理导出。
3. **仓库或目标基线改变时，重新判断包的适用性。** 显示“3 份产物中 1 份受影响”，而非“17 个文件变化”。同一原因聚成一束，避免制造告警墙。
4. **展开影响解释。** 例如“`consumer.ts` 的改动引用了旧接口记录；测试证据也早于后来修改”，给路径、版本、来源和具体检查，不只输出风险分数。
5. **用户或 Agent 执行定向重读/修补/重验。** 使用当前明确根目录与选定检查；有限次数失败后保留现场并进入现有裁决通道，不无限重试，不自动运行未授权网络操作。
6. **生成新的验证记录，而非覆盖旧绿灯。** 旧包仍是历史记录；新包对本次范围有效。若依赖还在变、检查未完成或覆盖未知，不给当前有效标签。
7. **交给另一会话仍可核验。** CLI JSON、恢复卡和只读 MCP 展示同一份账本投影；新模型不必拿到上一个 provider 的内部 session 才能知道包的版本和限制。

**完成点：** 用户能从“上次的工作还能用吗”走到“哪些检查在什么状态上通过、哪些没有覆盖”。不把“包当前有效”叫“已合并/已发布”，也不新增自动代码合并。

### 6.3 最小必要的数据对象

| 对象 | 必要内容 | 不能偷换的含义 |
| --- | --- | --- |
| 输入观察 | repo/worktree/path、版本、读取片段、捕获来源、强度 | 观察过不等于模型实际依赖 |
| 产物记录 | 代码片段/补丁/接口/评审结论的身份和版本 | 消息说“完成”不是产物验证 |
| 依赖证据 | 来源类型、上游版本、作用范围、记录时点 | 静态 imports 和模型自报不是同等级因果证明 |
| 验证记录 | 执行命令身份、cwd、代码状态、范围、终态、用例计数/报告摘要 | 退出 0 不自动变成全部需求满足 |
| 影响/重验事项 | 哪个变化使哪个包待核、处理记录、新证据或例外 | 通知 delivered 和前提解决分别存 |

源数据经 Blackboard 读写；状态由事件投影得到，不建立另一个 UI 真相源。新的产物有效性属于世界事实；线程只引用它，保持 ADR-0010 的世界/会话方向性，不把 `done/passed` 塞进 `thread.*` 事件。

### 6.4 依赖怎么来：这是主要研发难点

推荐三条可并存、必须可解释的来源：

- **明确声明的依赖。** 验证命令或受控产物记录声明输入清单，最容易审计，但不能要求用户手填每条代码边。
- **结构性候选。** JS/TS import、已登记接口、测试 runner 已知依赖、项目配置/lockfile/规范引用。能降低漏查，不等于完备语义依赖。
- **观察性候选。** 同一工作单元实际供给的版本、工具读取与产物的时间窗口。默认保守关联；不能把“读过文件 A 后写 B”自动标成强因果。

每条边保留来源，缺少足够范围时扩大到包级检查或返回未知，而不是为了少跑测试剪掉不确定依赖。完整动态 import、运行时生成关系、外部服务和模型隐含知识第一版不承诺解决。

**不建议第一步就上向量库或让另一个 LLM 猜所有依赖。** 模型可以提出候选解释，不能独自签发当前有效。

### 6.5 当前版本与当前基线要分开

身份至少区分仓库、worktree、相对路径和内容版本。交接包同时保留：

- 产物形成时实际看到的状态；
- 当前工位的状态；
- 计划用于比较/集成的目标基线。

主线变更并不意味着隔离工位磁盘已经改变。反过来，本地未提交改动也不能被一个相同 HEAD 忽略。验证绑定应覆盖 dirty/untracked 输入；不把 `git add` 或同内容提交当业务变化。

验证前后哈希相同只能排除部分变化，不能证明整个验证期间没有变化或没有 ABA。需要强结论时在明确的稳定副本上执行；无法取得稳定输入时标记未知。不能宣称由此获得全仓事务。

### 6.6 只管自己拥有的门，不冒充全局安全边界

第一版门可以约束：**Workbench 对交接包的“当前有效”判定及其自身的完成/重验入口。** 它不应声称能阻止所有编辑器、Git 或 Shell 写入。

- 原 seal 继续按其实际接入边界披露，不用新功能掩盖 Codex 的观测缺口。
- 未接入写者可通过磁盘差异使验证证据过期，但不能被伪造为已知作者或完整读取来源。
- 用户接受例外时记录独立结论；例外不是 passed。
- 只重读不改代码可以是合理处理，但必须说明依据，且不自动称为程序已修复。
- 重新验证仍失败、超时、0 个应有用例、运行途中改动、检查范围不足分别记录，不压成“失败/成功”一个按钮。

### 6.7 CLI / UI 应如何呈现

建议增加一条 CLI 主链，而不是先搭新看板。以下是**拟议命令，不是当前产品命令**：

```text
workbench revalidate inspect <bundle-id> --base <ref> --json
workbench revalidate run <bundle-id> --checks <declared-check-set> --json
workbench revalidate explain <bundle-id> --json
```

名字可在实现前调整，重点是“检查 / 执行已声明检查 / 解释”三种效果不混用。`inspect` 不启动模型或改代码；任何修补都走显式允许的现有会话/工位；检查报告能够导出，不自动上传。

恢复卡只增加一块结果：**仍可复用、需要重验、未覆盖**，这三项是事实清单，不是三级概率告警。提供一条可操作入口和展开证据；不新增全局树导航，不让用户先选择复杂流程。

## 7. 护城河应该积累在哪里

### 7.1 技术壁垒：低接入成本下的覆盖质量

最难复制的不是一个哈希判断，而是：外部 CLI 输出变化、分段读取、多版本片段、fork 边界、失败回合、实际 cwd、dirty 文件、测试输入和缺失证据，能长期保持同一种可解释语义。

需要一个 Windows 上的适配一致性矩阵：同一组读取/改动/失败场景经 Claude、Codex、显式导入走到统一结果。缺少真实通道样本时标未验证，不拿模拟样本替代。不要把适配器数量当覆盖质量。

### 7.2 数据壁垒：可回放、可判定的失败样本，而非原始日志体积

积累的是“变更发生在哪一步—系统看到了什么—哪些产物变得不可靠—最终哪些检查发现了问题”的带判据样本。包括漏报、无关变化、错误根目录、旧验证、通知无效、重验后再变等。

本地优先意味着没有天然跨客户数据网络效应。原始日志属于用户，默认不上传；公共语料应以合成最小复现、明确许可的开源案例或用户主动脱敏导出为主。**仓库私有、没有分发和使用规模时，不能把未来数据资产说成现成护城河。**

### 7.3 使用积累：可迁移的项目级证据，而非供应商锁定

一个项目反复使用后，可以沉淀可信验证配方、结构性依赖、已处理变化和包间关系。换模型或换会话不需要重建全部认知。这种累计价值应可导出，不靠困住用户维持。

但过期数据也是负资产：任何缓存或索引要有来源、失效规则和重建路径。没有真实维护能力，图越大越容易变成第二个过时 README。

### 7.4 分发与集成：当工具间的接口层，而非要求换 IDE

优先让已有终端/CLI 用户得到第一份有价值的交接包，而非要求迁入一个新工作台。只读 MCP、JSON 和文件格式让其他宿主消费结果；面板是解释器，不是强制入口。

当前仓库仍私有、npm 未公开发布。**这是分发边界，不是本轮应擅自公开的缺陷。** 若目标是市场壁垒，单机工程深度本身不等于市场壁垒；在现有永久退役的研究范围下，也不能声称已经证明留存、付费或生产率提升。

### 7.5 简洁的价值判断模型

一次额外检查是否值得，取决于：

`预计避免的缺陷损失 + 节省的重复核查成本 − 重验成本 − 误报带来的中断成本 − 集成维护成本`。

本轮没有代入虚构参数。对小仓库，“全部重读 + 全量测试”可能更便宜、更可靠。如果新方案不能在明确的受控工作负载上保持结果质量并减少不必要工作，就应该收缩，而不是继续用更多模块解释价值。

## 8. 扩展顺序与明确不做的事

下面是**候选实施顺序**，不是已排期任务。它满足 ADR-0023 要求的“新研究问题与验收”，但不自行改写其冻结边界；真正实施前应以新 ADR 明确取代/扩展关系。

### 阶段一：先让证据不说过头

- 多片段/多版本读取保留，单独记录范围被淘汰或不可比较。
- 送达状态与待重验状态分离；修正 repaired 指标语义。
- 验证记录绑定代码/命令/范围，checkpoint 推进时重新判断证据是否仍适用。
- 已修 #45–#48 与已运行读数完成原有落地手续，不重新做一遍相同修复。

**退出标准：** 五组本轮反例成为可解释且被覆盖的契约；未知不会被判当前有效。先不要拓展模型数量。

### 阶段二：完成一个交接场景，而非十个半成品

选择 JS/TS 单仓、一个 Agent + 人类编辑、隔天恢复/目标基线变化。交接包同时覆盖输入观察、一个产物、相关检查和恢复卡。

**退出标准：** 从已有工作恢复，经变化解释与定向重验，得到绑定当前代码的结果；缺样本/检查失败路径也可结束且可追溯。不依赖用户先手填依赖图。

### 阶段三：再扩大到多工位和异构会话

在上述切片成立后，加入 repo/worktree 身份、跨分支基线、独立新会话消费、批处理导入。优先验证两个通道语义一致，而非声称任意 provider 内部记忆可迁移。

**退出标准：** 同一产物换持有者仍保留原始依据；新的读取不能洗掉旧产物的来源；主线变更与工位变更可分辨；修补结果与验证范围一致。

### 暂不选择

- 通用多 Agent 平台、复杂角色树或大而全 DAG UI。
- 自动语义合并、全仓排他锁、通用 saga、任意副作用回滚。
- 自建容器/数据库/预览环境平台。
- 用签名或区块链替代来源真实性；同机可信执行边界没建立时，签名不能证明检查真的运行。
- 大规模任意 Shell 解析器。优先结构化事件、显式导入和受控检查命令。
- 重新开启真人自然使用、生产率研究、非 Windows 执行或 CI。

## 9. 怎样验证“拓展有价值”，而不是只增加测试数

### 9.1 研究问题

**在部分工具可观测、历史会话不能完全搬运的条件下，产物级来源与范围化重验，能否减少受控变更场景中的“过期证据被当成当前有效”，同时不增加对照集中的回归或把无关变更全部升级成全量重做？**

这是机制有效性问题，不是被退役的自然生产率研究。

### 9.2 必须保留的基线

1. 没有额外协调，直接继续原任务。
2. 当前 Workbench：读集提示与现有恢复卡。
3. 粗粒度代码指纹 + 每次全量重跑检查。
4. 交接包 + 范围化重验。

“回执型门”的独立参考可用 Stalegreen 的公开设计，但如果没有实际安装跑它，就写“本地实现的粗粒度基线”，**不能标成击败 Stalegreen**。所有方法在同一任务、同一检查能力和预算下比较。

### 9.3 关键测试矩阵

至少覆盖：无变化、无关文件变化、同文件不同片段、多段读取、跨文件接口变化、规范/lockfile 改动、无目标读取、通知后未复读、复读后仍旧计划、测试后再次编辑、测试期间编辑、分叉继承来源缺失、换 worktree、目标基线推进、校验工具失败、0 用例/子集被称全量、重试中断、快照被淘汰。

可在 Windows 隔离仓库与脚本化假 provider 中复算。不把脚本化模型行为当 live-model 效果。可用条件下的 Codex 实验仍独立记账；此次用户给的是搜索 key，不是编码模型运行授权。

### 9.4 判据与停止条件

- 对声明必查输入缺失、范围未知、验证失败或运行期间状态不稳定，**不得给当前有效**。
- 通知送达、只读了一遍文件，均不能独自满足产物验证门。
- 单次通过只绑定自己的输入范围；旧记录保留，不洗成新记录。
- 记录可检测缺陷逃逸、无关变化引起的无效重验、执行检查集合、代码/日志读取量、耗时分布和失败原因。默认不以 token 或 agent 数作为成功指标。
- 第一阶段要求确定性契约用例零错误“当前有效”；这是验收目标，不是总体零漏报保证。
- **停止/收缩条件：** 依赖声明维护比全量检查还费事；范围缩小使回归增加；宿主无法给足身份信息；检查成本本来很低；使用场景只需一个轻量回执插件。出现这些情况时，保留轻量证据链即可，不继续建平台。
