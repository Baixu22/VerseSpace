## 4. 执行节奏与复拍规则

1. **补基线**：先完成要修改的场景和状态。隔离工作区、固定文本与配置，不使用个人对话或密钥。沿用 `scripts/win/e2e-browser.ps1` 的启动方式和现有 Playwright 依赖。
2. **每批只处理一组问题**：第一批输入区与文字，第二批侧栏与操作状态，第三批有内容的消息/恢复/证据。每批以截图发现为修改入口，复拍仍有问题就继续修该批。
3. **同条件复拍**：同一场景 ID、视口、缩放、DPR、主题、数据、滚动位置和展开状态。字体完成加载、有限动画结束、内容断言成立后截图；不能只靠延时或 `networkidle` 判断流式页面完成。
4. **打开图片逐张检查**：脚本产生路径不等于看过图片。每条问题记录 `before → 修改文件 → after → 操作检查 → 通过/未通过`。原始全图保留；可另附局部对照，但不能裁掉错误/状态信息来制造通过。
5. **通过才选入 README**：到最终候选提交重新采集成品图。若后续又改了对应 UI，重新拍摄；不沿用旧图冒充新版本。

每张图最少记录：场景 ID、日期、受测 commit、dirty 状态及补丁身份、数据准备方法、浏览器版本、视口/DPR/主题、操作步骤、PNG 路径与 SHA256、肉眼检查结果。采集脚本和演示数据准备方法应随最终实现入库；原始日志、浏览器 trace 与临时现场继续留本机。不要为此引入截图服务或新的 CI。

建议用现有 Playwright 增加一个范围明确的截图场景文件，或在相应成功检查后显式 `page.screenshot()`。当前 `screenshot: "only-on-failure"` 无法产出稳定的成品图库；保留失败截图策略，额外捕获被选中的成功场景即可。初轮先人工检查前后图片，不引入脆弱的全页逐像素阈值。
