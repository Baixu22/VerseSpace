# Workbench 0.5.0 候选工程收口

受测对象是 `@baixu22/workbench` **`0.5.0` 源码候选**。本版没有创建
`workbench-v0.5.0` tag、GitHub Release 或 npm 发布；当前公开发行仍是
`workbench-v0.4.1`，旧二进制不包含本记录中的产物证据能力。

## 交付内容

- checkpoint 可显式绑定历史输入、footprint 序号、selector、内容摘要与来源强度；
  文件采样、弱来源、晚登记和返回后竞态保持 unknown。
- 固定文件检查在复制对象中执行并记录实际字节、runner、报告和对象摘要；源文件临时
  改写不穿透副本。输入、产物、脚本、配置和目标范围变化分别触发重验。
- 严格 1 MB 便携 manifest 只含相对路径、摘要、范围、runner 目标和来源身份；接收方
  在显式工位核对实际字节与本机策略，可选择使用本机已有的固定文件检查重验。
- CLI、只读 MCP 与恢复 GET 使用同一有限产物投影。现有恢复卡展示 current / stale /
  pending / failed / unknown，以及来源、输入、检查、目标、refs 和 CLI 重验命令；
  查看和复制不写有效性，也不执行命令。
- 冻结受控重放覆盖强朴素、旧主线和三项消融。增强声明范围为零 false-current、
  false-reject、来源错配和 unknown；四次不变消费的完整检查次数为 1，强朴素为 4。
- 三个 ledger 尺度的增强总时间均未低于朴素，因此没有总体时间净收益；该结果原样保留，
  不把调用次数下降包装成性能优势。

## Codex 当前边界

本轮用当前 Codex 26.1021、隔离 `CODEX_HOME`、显式 `apply_patch_tool_type=freeform`
和本机非敏感 provider catalog 重跑成对仪。两轮读取均完成，native writeMode 明确：

- own-fresh：原生写入落盘，writeFootprints=1，readDuringWrite=0，但 seal 事件=0；
- own-stale：1 条本写者失效前提，冻结控制判 block，但原生写入仍落盘，
  writeFootprints=1，seal 事件=0。

成对仪因此为 `passed=0 / total=2`、exit 1。旧 Codex 0.159 的 2/2 正面对照已改为历史
observation，只解释该旧版本；当前候选没有通过 Codex 写保护声明。该负向读数不阻塞本机
Workbench 主套件，但明确限制了“护城河”可叙事范围。

## 结论边界

工程证据证明的是固定 Windows/本地单仓/单产物范围内的来源、范围、副本、消费和可携带
复核。它不证明所有工具/写者覆盖，不证明真实模型或真人效率，不证明市场护城河、跨平台
执行、容量上限或合并后的语义正确。`0.5.0` 在没有后续明确授权时不打 tag、不创建
Release；README、CHANGELOG、构建资产和最终森林证据必须指向同一候选选择。
