## 0. 你的角色与任务

你是一名横跨 HCI、分布式系统与开发者工具的资深架构评审。委托方维护一个单人项目 **Workbench**:本地优先的 CLI + 文件系统状态管理器,为 AI 辅助开发管理"项目元结构"(目标 DAG、架构决策、接口契约、git worktree 工位、checkpoint 验证、事件审计,以及**对话本身**)。类比物是 git / turborepo——它们管理代码的元结构,Workbench 管理 AI 协作的结构。它已按三条支柱建成第一批能力:**交互层**(L0–L2)、**会话树**(分叉/恢复)、**并发**(建议式前提失效检测)。

你的任务,在 §3.4 红线内完成:(a) 对项目根命题的系统性攻击;(b) 三支柱统一抽象的判断;(c) merge-back 语义设计;(d) 失败模式审计;以及按优先级的深化问题。你的输出直接决定未来三个月的路线与砍留。委托方最大的心病:**整个体系 117/119 个任务节点从未经过"真实使用有没有用"的检验——为做而做的风险由你一并审判。**

## 3. 背景(唯一事实来源)

### 3.1 系统骨架:两条数据流 + 三个刻意断层

规模:160 个 TS 源文件(56 测试文件,约 1.47 万行源码+0.9 万行测试),零数据库(状态=仓库内 `.workbench/` 的 YAML+JSONL),零重依赖红线;全量测试 355 例。另有冻结的 legacy 桌面应用(ADR-0003)与一个自管理任务图(119 节点)。

**执行管线(代码层)**:goal(CAS 版本+验收断言)→ dispatch(CONWIP 令牌准入,拒绝时**先于任何创建**,不留半成品 worktree)→ workspot(git worktree + 自动生成 `.agent-context.md`)→ agent 产出 → checkpoint(staging/verified/failed 三区,含 `blackboardEffects` 写集声明位)→ verifier(worktree 内跑 test/type-check/build,按 exit code 判)→ 接口注册表(contentHash 漂移检测 + version CAS,不匹配抛冲突)→ 漂移传播。后台 watcher 每轮比对各写者读集→失效前提写进事件日志。

**会话管线(对话层)**:每线程一个持久 claude CLI 子进程(stream-json 双向,`--session-id`/`--resume`);每次 tool-call 抽足迹(读集 `used` 带调用时哈希+行级 span,写集 `generated` 带结果哈希,64KB 内容暂存供 diff);`premises.ts` 每轮比对读集发 `premise_stale`(三层判定:耐久分层→span 重定位→导出面哈希);`delivery.ts` 投递;`notifySession` 注回活会话(轮间注入,追加式,KV-cache 安全)或排队下轮前。

**事件流真相**:一条共享 append-only 日志 `events.jsonl`(seq=行号=因果时钟;source 域含 runtime/scheduler/agents/tribunal/sessions/interactions/premise/restore)+ 各写者 `footprint.jsonl`(**刻意双写**进共享日志,"two stores, one truth")+ chat 私有 `messages.jsonl`。**断层一**:fork/leave/restore/reload **没有任何一等事件类型**(0 处)——分叉只写 `meta.forkOf` 血统与 `meta.forks` 计数,不产生事件。**断层二**:chat 足迹在记,但被刻意排除在车道计量外(代码注释:"a thread is not a lane")。**断层三**:interactions(L1 隐式上下文)是建好的纯函数库(DOI 公式+衰减+生命周期自适应常数),但 `computeDoi`/`projectLandmarks` 在其目录外**零 import**——无人消费;人类 selection 信号不存在(注释:"人类侧:未来由前端交互层直接上报")。

**唯一例外**:全系统"永不阻断",但存在一个被祝圣的封印点(`seal.ts`):Claude PreToolUse hook,写进已知漂移区域则 exit 2+证据进 stderr(原文:"基于已失效的前提写下去,事后返工的代价远高于现在停一下")。封印不持久化,hook 时重算。

**机器层接线状态:零未接线**。runtime/tribunal(ISA-18.2 裁决队列:五道定性门+5/15/30/50 目标分布+NEWS2 三红[auth/force-push/secret]直升 critical;无推送通道,pull-only)/scheduler/verifier/automaton(三个纯函数状态机)/doctor/contextgen/agents(crash 熔断+车道困境检测)/supervisor(树杀/pid 注册表/stdin 门控)全部有命令、周期或端点到达。唯二"形状已定义无生产者":promote 的 `repeated-test-failure` 与 `commit` 两个晋升信号("由足迹侧喂入,本层只定义形状")。**WIP**:`L=λ×W` 从事件日志实测推导(完成样本<3 时明说 `insufficient-history` 退回物理上限;CONWIP 全局令牌;`--force` 只留给人,自动调度器无权)。

> 2026-09-26 补记(issue #36):promote 的这两个"形状已定义无生产者"变体已从 `PromotionSignal` 删除——声明只保留库内真有生产者的三种形状(`turns-crossed` / `next-day-resume` / `second-fork`),与真实边界一致(ADR-0023)。本节以下 §3.2 表"未建"列与 T4 里的同一提法均以此补记为准;原文保持原样。

**GUI 现状**(web,嵌入二进制):每条消息 hover"分叉"(零仪式)、备选只读面板(无选择界面)、恢复笔记条、决策账本(无分歧不渲染)、停放条、建议条、plan 批准卡、线程侧栏平铺+分叉血统徽标(无树视图)。**没有**:DOI 任何 UI;promote 端点从未被 GUI 调用;**drafts/parked 是浏览器内存态不落盘**;CLI 没有任何 tree/fork/thread 命令(chat 完全活在 HTTP 层)。

### 3.5 数据清单(证据分级)

**本机实测**:晋升成本 B=3ms、拆除 C=12ms、worktree remove 1.30s;`git merge-tree` 热态 33ms(2053 文件,Windows);R3 验收:队列 0.75 条/h(上限 6)、critical 5.6%(≤25%)、分布≈5/15/30/50;人类容量 ~1 条裁决/10 分钟(队列常量注释);Windows FS 慢(删除 350–500ms/条);git 2.55.0.windows.3 无法建含 `/` 分支名(本机阻断 dispatch)。

**文献引用**:CoAgent(arXiv:2606.15376,十竞争负载):2PL 悲观锁 1.04×/每轮死锁 0.81;OCC 全量重试 0.93×/token 1.83×;**MTPO 建议式通知 1.4×/正确性差≤5%**;无协调并行通过率 13%。ConE(arXiv:2101.06542,微软 234 仓库生产):不做推测式合并,只发文件重叠信号,26000 PR→775 通知(3%),70% 有用,>90% 愿续用,明确拒绝 ML("精度太低,误报太多会让工具无人使用")。Mylyn(唯一带 p 值的 DOI 胜利):p=0.003;84.17% 选择落在正 DOI 元素;**容忍约 28% 假事件**——"一个 28% 错误的产物带来可测的生产率提升,因为没有任何东西依赖它正确,也没人需要批准它";但其常数"对任务生命周期盲"(两个方向同时失败)。TaskSnap(清场,n=55):编辑延迟 4.81 vs 6.10 分钟,无关产物 1.21 vs 20.28——**清场是一半效果**。InkSync:验证界面使被接受的错误编辑 −44%,审计抓 73%——**验证界面胜过探索界面**。Leroy & Glomb(离开时起草):自动线索组成功率是自记组两倍。挂起工作可见度 <25% → 返回时间显著更长(仅仅看得见就是提醒)。撤销作负样本:误报率 0%,暴露 92% 严重问题。Dow 平行原型(n=33):44 vs 26 真实点击。GPT-5 自动路由:使用率 7%→24%——"3 倍差距纯由'要求选一次'造成"。**Letta 纯文件系统 74.0% 打败 Mem0 结构化抽取 68.5%——"抽取销毁了信息"**。打断代价(随机 vs 任务边界):恢复时间 +30%、错误 2×、负面情绪 2×。用户保持模式状态比系统保持的视觉反馈好 3 倍(ω² 15.6% vs 4.8%),系统"锁定式"指示与无指示统计不可区分。生成式 UI:50.8% 胜/41.1% 负(掷硬币)。ISA-18.2:工厂跑合理化流程删 40–60% 报警。LLM 语义合并与开发者一致率 55–59%。Horvitz 期望效用几何:p<K/B 沉默、K/B≤p≤1−K/C 提议、p>1−K/C 直接做;**K(1/B+1/C)>1 时提议区间为空**(本机已实测落入此情形)。

### 3.9 当前假设 H1–H6(委托方的倾向,供攻击,不是结论)

- **H1 分支间前提失效**:分叉时刻从继承前缀的已记录足迹为新分支合成初始读集,复用现有 reconcile 循环——兄弟分支写盘后,本分支的继承前提自动失效。
- **H2 恢复双通道**:恢复笔记(叙事,离开时已生成)+ R2′ 读集 diff(仓库事实,返回时计算)合成一张恢复卡;冲突时事实优先并标注。
- **H3 DOI 做树的清理学**:低 DOI 分支自动降权/归档(可逆),归档不删除。
- **H4 分叉时刻是唯一的零成本结构化时刻**:C1 禁每会话前置成本,但 fork 低频、高信息、用户主动——`ForkDeclaration` 可携带从继承前缀足迹推导的 touch-scope(用户零输入)。
- **H5 merge-back 最小语义**:不合并内容;把分支的恢复笔记+决策账本差异+(若碰代码)merge-guard 预测与接口版本变化,作为一条系统消息注回源线程;一次手势+改回即撤销。
- **H6 三支柱统一事件流**:fork/leave/restore/merge-back 升格为一等事件并入 events.jsonl,使"哪些分支的前提失效了""哪些分支的 DOI 在衰减"成为同一流上的查询。

## 4. 问题集

### 第一优先(必答,不得省略)

**Q0 · 攻击前提(元问题,最先答)**
三支柱共同押注的根命题:"单会话线性交互结构性地丢失试错历史与决策理由,且这个损失大到值得为其重建交互模型。"请:(a) 给出对这个根命题最强的三条反驳(包括但不限于:用户可能只想更好的线性恢复;"岔开冲动"可能天然 <1 次/周——这会触发 §3.9 的证伪线;树的价值可能被 git+会话摘要 90% 覆盖);(b) 每条反驳配一个**成本最低、判决最快**的验证实验(≤1 周工程量,可复用现有 L2 部件);(c) 明确:哪些反驳若成立,三支柱中哪根该砍、哪些已建代码能无损保留。
输出:表格(反驳|成立时的迹象|判决实验|砍什么留什么)。质量标准:攻击根命题而非实现细节;实验两周内可出数;砍留具体到已建部件。

**Q1 · 统一抽象:三支柱是一层还是三视图?**
系统底座是 append-only 事件流 + 派生投影。交互(DOI 显著性)、树(决策拓扑:fork/variant/merge)、并发(前提失效:读集 vs 世界)是否可建模为**同一条执行流上的三个投影**?若可以:给出统一事件原语的最小 schema(字段、不变量,每字段过"后到事实会推翻它吗"的单调性判据),fork/leave/restore/merge-back 如何成为一等事件,现有流如何无损迁移。若不可以:给出精确的不可统一论证(哪两个投影在什么不变量上冲突)。
输出:schema 草案+不变量清单+迁移路径,或反证论证。质量标准:每字段标单调性;能同时表达全部已建行为且不违反 R4/R7;迁移不引入数据库(R11);必须说明与 TF-0118("a thread is not a lane")边界的关系。

**Q2 · merge-back 的最小正确语义(树线最大缺口,竞品确认的空白)**
在 R5(无提议 UI,直接做+廉价撤销)、R7(加法式)、R8(三个恢复动作分开)、R12(拆除≤undo)下设计 merge-back:(a) **语义三级**(引用指针/摘要注入/内容合并)各自失败模式、适用判定条件、与 merge-guard 和接口注册表的交互——分支碰过代码时,回注应携带什么并发层事实?(b) 回注物在源线程的呈现形态(不得违反 R7 与"无分歧不渲染");(c) 与 H5 对比:缺了什么、多了什么;(d) 验收标准。**必须处理 Letta/Mem0 证据("抽取销毁了信息",见 §3.5)与"人们很少回头"(纯指针无人点开)的对抗。**
输出:语义矩阵(级别×失败模式×判定条件×undo 方式)+一个端到端用户故事(fork→分支工作→merge-back 全序列)+信息形态谱系的推荐(纯指针/指针+一行摘要/摘要+溯源链接/完整轨迹追加,各标信息损失、被消费概率、错了的回退路径)。质量标准:包含"回注稀释主线上下文"这类二阶效应;无确认对话框;说清与 meta.forkOf/账本/恢复笔记的数据关系;给出信任模型(用户何时开始信任回注物)。

**Q6 · 失败模式审计("看起来很美但会崩"清单)**
对三支柱组合给出**至少六种**失败模式,必须覆盖:(1) 恢复笔记过时/幻觉误导(叙事与仓库漂移——注意:流畅叙事本身是被包装的确定性,比沉默更危险);(2) 树熵(分支无限增长);(3) 通知洪泛(fork 扇出放大写者数,chat 层通知无队列限速);(4) 沉默伪装安全(精度优先→用户过度信任"没消息=没问题");(5) merge-back 污染主线(主线上下文稀释);(6) METR 陷阱(恢复/账本界面增加阅读时间,验证成本对用户不可见——用户无法报告它在失败)。**至少一条是你自己发现的不在上面清单里的。**每个给出:早期检测信号(必须是现有系统已记录或一行代码可记录的量)、熔断设计(必须是关开关而非回滚架构,兼容 R12)、首现用户画像。
输出:失败矩阵(失败模式|检测信号|熔断|首现画像)。

### 第二优先

**Q3 · 分支作为写者:把 R2 从"写者间"扩展到"分支间"**
现状:fork 新线程无读集,兄弟分支写盘后其继承前提静默失效。设计:(a) H1 方案(分叉时从继承前缀足迹合成初始读集)的正确性边界——何时漏报/误报?足迹哪些该进(used/generated/span/64KB 暂存)哪些不该;(b) 分叉事件携带 touch-scope(从足迹推导,零用户输入,H4)能否化解 C1 摊销矛盾——给出摊销算术(区分"每会话"[C1 禁止]与"每分叉事件"[低频可摊]);(c) 此机制为 merge-back 裁决提供什么;(d) 与 R9(精度优先)的张力:分支间误报的下游自纠路径存在吗?
输出:机制草图(数据流级)+失效模式表+摊销算术。质量标准:复用现有 premises/delivery/footprint 部件;回答"为什么这不是编排器"(R10)。

**Q4 · 恢复的双通道:叙事+仓库事实如何合成"回来时的处境"**
(a) 恢复卡信息架构:节拍(叙事)与前提漂移(事实)的排列/优先级/折叠层级(遵守 R7 与"无分歧不渲染");(b) **冲突语义**:叙事说"动了 X"但仓库显示 X 已被回滚/被第三方改写——哪边赢,呈现规则;(c) decided 拍升级路径:在不增加记录负担前提下,"为什么放弃另一条"的最大信息源是什么——N=2 重放当场算,还是别的;(d) 处理退化情形(离开很久且仓库大变)。给出与现有验收句("隔天恢复无需翻 git log")兼容的验收升级。
输出:恢复卡线框(ASCII)+冲突规则表+验收句。质量标准:零新仪式;冲突规则可被测试表达。

**Q9 · 人的 WIP 是否纳入 CONWIP**
系统把复核者当鼓点,CONWIP 只 gate agent 派发;但人是最终瓶颈却不受任何 gate(legacy 经验:"the limit is your review bandwidth";裁决队列常量承认人类容量 ~1 条/10 分钟)。设计(或否决)"复核者 WIP":候选干预点(分叉手势/新线程创建/派发[已有 gate]),各标家长式风险与最小干预形态(可见?软提醒?硬 gate?)。硬 gate 若被推荐,必须给出何时退化为软提醒、用户如何永久关闭(R7 对称退出);若否决,给出自由放任方案及可观测风险。
输出:干预点矩阵+推荐+否决论证(若否决)。

**Q10 · chat/world 边界的终态(统一事件流 vs 翻译层)**
三支柱合流的每个方案(H1/H2/H5)都被"a thread is not a lane"的隐形边界卡住。给出终态设计或反证:统一后**可执行的新查询清单**(跨对话与代码的,至少 3 条,每条表述为"省掉一次人的什么动作";若一条都举不出,统一即伪需求);什么**必须不统一**(TF-0118 的顾虑在统一后如何安置);迁移路径(R11;对 R3"agent 自称完成不可信"的影响必须讨论)。
