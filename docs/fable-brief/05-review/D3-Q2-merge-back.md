# D3 · Q2 merge-back 的最小正确语义

## 先定性:merge-back 不是一个动作,是恢复卡上的一拍

R5 禁止"要不要合并?"提议 UI,Horvitz 几何在本机已落入"提议区间恒空"(K(1/B+1/C)>1,【本机实测】)——所以 merge-back 只能是"直接做 + 廉价可逆"。"直接做"需要一个触发点。候选:
- 分支"结束"时——线程没有结束,只有离开;离开不是结论。
- 用户在分支里点"带回主线"——是显式手势,允许,但会变成一种仪式(R6:用户不会养成习惯)。
- **用户回到源线程的那一刻**——这是已有的恢复时刻(H2 的恢复卡),分支的动静天然是"你不在时脚下动了什么"的一种。

结论:**merge-back = 恢复卡的"分支动静"一拍**(自动、零手势、加法式),外加**一个**显式手势"以分支为主线"(adopt,改身份不改内容)。H5 没有定义触发点;这是与 H5 最大的差别。

## (a) 语义三级矩阵

| 级别 | 携带什么 | 失败模式 | 适用判定(自动,零输入) | 与 merge-guard / 接口注册表的交互 | undo |
| --- | --- | --- | --- | --- | --- |
| **L0 指针** | "分支 C(自 #k 分出)有 N 条新消息 [打开]" | 无人点开("人们很少回头");零信息损失;零稀释 | 分支有新消息但**无**账本差、无写集、无接口变化(纯探索分支) | 无 | 隐藏(一次手势) |
| **L1 结构摘要**(推荐默认) | 指针 + 一行:账本差(选了 variant 2/3;采纳/拒绝了哪些建议)· 写集(N 文件,hash)· 接口版本 Δ(Foo v3→v4)· merge-guard 预测(若分支在独立工位:merge-tree clean/conflict + 重叠账本)· **Verifier 状态**(verified@cp-7 / "未经 Verifier")· 分支自身失效前提数 | 事实为真但"为什么"缺席(R1 悖论,不可修);分支只读不写时摘要为空 → 退化为 L0;若把叙事塞进来 → Letta/Mem0 的"抽取销毁信息" | 分支有 ≥1 账本差 或 ≥1 写 或 ≥1 接口 Δ | **共享工作树**:分支写集 ∩ 源线程读集 → 已由 R2 投递为 premise_stale,摘要只引用(不重复投递)。**独立工位**:git merge-tree(33ms【本机实测】)预测 + 30min 重叠账本;CAS 冲突若分支抛过,列为账本条目 | 隐藏 + 撤回下一轮注入(未投递时完全撤;已投递则不再重复,但不回滚已生成的回应——R4 不整体回滚) |
| **L1.5 以分支为主线(adopt)** | 不搬内容:子线程成为主线程,源线程归档(仍可见、可反转) | 用户误以为源线程 #k 之后的消息"合并进来了"——没有;需标签明说"源线程自 #k 后的 M 条不在此线程" | 仅显式手势 | 无(拓扑操作) | `thread.adoption_reverted`,一次手势 |
| **L2 内容合并**(否决) | 把分支消息追加/交错进源线程上下文 | 伪造无人经历过的线性史(ChatGPT 坟场);双方决定矛盾时模型上下文自相冲突(LLM 语义合并一致率 55–59% = 掷硬币【文献引用】);模型读过即不可撤(违反 R12);源线程"逐字节不动"的保证被破 | 永不 | 代码层的合并是 git 的事;Workbench 只出预测(R4 拒绝 CRDT/合并,R10 不是编排器) | 不存在干净回退 |

**分支碰过代码时必须携带的并发层事实**(按信息价值排序):
1. Verifier 对分支最后一个 checkpoint 的裁决(R3:没有就写"未经 Verifier",绝不写"完成")。
2. 分支写集与源线程读集的交集——引用已投递的 premise_stale 事件(不重复发)。
3. 独立工位时:merge-tree 预测 + 重叠账本;共享工作树时:此项不存在(改动已经在树上)。
4. 接口注册表:contentHash 漂移与 version CAS 变化。
5. 分支在其生命周期内自身失效的前提数——"分支的结论建立在 3 个已失效前提上"是 R3 风格的诚实标记。

## (b) 在源线程的呈现形态

- 位置:**恢复卡内**,作为"你不在时"的一节;不在分叉点插入(那里已有血统徽标),不打断历史。
- 形态:每个有动静的分支一行,折叠;≥3 个分支有动静时合并为一行"3 个分支有动静 [展开]"(与 tribunal 同样的合并纪律)。
- **无分歧不渲染**:分支无账本差、无写、无接口 Δ、无新消息 → 不渲染任何东西(徽标已足够)。
- 每个事实带溯源(`refs` → seq / ledger 条目 / diff);**没有证据的行不渲染**(I7)。
- 叙事(分支离开时起草的恢复笔记)只放在展开区,标"由足迹拼接",事实在前。
- 模型侧:同一事实块经 notifySession 轮间追加(KV-cache 安全),上限 ~300 token【你的假设】;叙事**不注入模型**。
- 手势:`[打开分支]`(恢复对话)`[看分支改动]`(代码)`[以分支为主线]`(adopt)。R8 三个动作分开且有标签;没有"两者"按钮,因为恢复卡本身就是"两者"。

## (c) 与 H5 对比

| | H5 | 本设计 |
| --- | --- | --- |
| 触发点 | 未定义 | 回到源线程的恢复时刻(零手势);adopt 为唯一显式手势 |
| 内容 | 分支恢复笔记 + 账本差 + merge-guard + 接口 Δ | 同,**加** Verifier 状态、分支自身失效前提数、premise_stale 引用而非重复 |
| 叙事位置 | 与事实并列 | 事实在前,叙事折叠且标"拼接";叙事不注入模型 |
| 门 | 无 | "无分歧不渲染"+ 无证据不渲染 + ≥3 合并 |
| 拓扑 | 无 | 新增 adopt(以分支为主线)与其反转 |
| undo | "改回即撤销" | 明确撤销的作用域:未投递完全撤;已投递不重复、不回滚回应 |
| 内容合并 | 不做 | 不做,并给出否决理由 |

H5 有而本设计砍掉的:没有——H5 的每一项都保留了,只是被排序、加门、加触发点。

## (d) 验收标准

1. **空分支零痕迹**:fork → 什么都不做 → 回源线程 → 无卡片、无注入、日志一条 `thread.restored` 而无 `merged_back`。
2. **全溯源**:渲染的每一行可解析到 ≥1 个 `seq`;测试对渲染输出做 refs 完整性断言。
3. **R3 措辞**:无 Verifier 事件时输出串含"未经 Verifier";含 Verifier 事件时输出串含 checkpoint id;两者互斥(快照测试)。
4. **注入上限**:模型侧注入 ≤300 token(可配置);每分支每次返回 ≤1 行;≥3 分支合并为 1 行。
5. **撤销**:dismiss 后 ≤K(2s)完成;下一轮注入队列中该块消失;日志新增 `merge_back_dismissed`。
6. **adopt 可逆**:adopt → revert 后线程可见性与 adopt 前逐项一致(快照)。
7. **fit 指标(两周真实使用)**:渲染的分支行中被展开或指针被点的比例 ≥50%;否则默认降为 L0。

## 信息形态谱系推荐

| 形态 | 信息损失 | 被消费概率 | 错了的回退路径 |
| --- | --- | --- | --- |
| 纯指针 | 0(原文可达) | 极低 | 不需要 |
| **指针 + 一行结构摘要** | 低(只丢叙事;叙事本来就 R1 不可得) | 中(一行在视线内;Mylyn 式"没人依赖它正确") | dismiss |
| 摘要 + 溯源链接 | 低 | 展开时高 | dismiss |
| 完整轨迹追加 | 0 但稀释(模型被迫消费) | 高且有害 | 无(模型已读) |

推荐:**渲染默认 = 指针 + 一行结构摘要;展开 = 溯源链接 + 折叠叙事;永不完整追加。** 这同时回应 Letta("抽取销毁信息"——所以不抽取,只列执行事实并留原文指针)与"人们很少回头"(所以一行事实必须能独立改变下一步行动:它列的是前提失效数与 Verifier 状态,这两项直接决定"能不能接着做")。

## 端到端用户故事

1. 周二 14:02,线程 P 讨论 token 刷新,agent 第 5 轮读了 `src/auth.ts`(h1)、`src/session.ts`(h2),提了方案甲。
2. 用户 hover 消息 #5 →「分叉」→ 线程 C 立刻出现。日志:`thread.forked{child:C, parent:P, at_message:#5}` + `footprint.inherited{refs:[P 的两条 footprint]}`。P 逐字节不动。(前提:C 的 agent 继承了上下文——D0 盲区。)
3. 用户在 C 说"走方案乙"。扇出 3 个 variant,展示 1 个,信号晋升 variant 2(`variant.promoted`)。C 的 agent 改 `src/session.ts`(h2→h3),跑测试,checkpoint cp-7 → Verifier verified。
4. watcher 下一轮:P 的前提 `session.ts@h2` 失效 → `premise_stale{actor: C}` 投递给 P(现有 R2)。P 若正活跃则轮间注入"你的前提 session.ts 已被分支 C 改写"。
5. 用户切回 P(离开 C → C 的 `thread.left` 起草笔记;P 的 `thread.restored`)。恢复卡:
   - 头行:"离开 41 分钟 · 1 个分支有动静 · 你的 1/12 前提已变"
   - 分支动静:"C(自 #5)· 选了 variant 2/3 · 写了 session.ts · verified@cp-7 · 使你 1 个前提失效 [打开] [看改动] [以 C 为主线]"
   - 日志:`thread.merged_back{from:C, into:P, level:summary, facts:{…refs}}`
6. 用户在 P 发下一条消息;agent 看到 ≤300 token 的事实块。或用户点 × → `merge_back_dismissed`,注入队列清空。
7. 隔天用户点"以 C 为主线" → `thread.adopted`;P 归档但可见,侧栏标"自 #5 后 3 条不在 C 中";点撤销 → `adoption_reverted`。

## 二阶效应与信任模型

- **回注稀释主线**:上限一行/分支、300 token/次、≥3 合并;dismiss 率 >50%(负样本)→ 自动降为 L0(D4 失败 5 的熔断)。
- **回注变成伪完成信号**:一行里若有"verified@cp-7"用户会当"做完了"——所以必须并列"分支自身 k 个前提已失效",且从不出现"完成"二字。
- **兄弟对称**:C 回到 P 的动静,P 对 C 也是"你不在时"——同一机制,方向对称,不需要额外设计。
- **信任建立**:用户信任回注物的条件是"每一行都能点开验证且从未错过"(InkSync:验证界面 −44% 错误接受)。因此宁缺毋滥(R9):无证据的行不出现;叙事永远折叠并标注来源。信任破裂的最快方式是一行错的"verified"。
- **信任成熟的迹象**:用户不再点开溯源、只扫一行就继续——这时 fit 指标 7 会下降,不要把它误判为噪声;辅以"返回后第一动作"指标(D6 Q4)交叉判断。
