> 这不是给模型的锋利问题——这是**还没有变成问题的直觉**。每簇结构:直觉(用户脑子里的画面)/ 比喻与厌恶 / 张力(两边都有证据支持的对立)/ 模糊问题(开放式,允许贵模型重构问题本身)。证据编号指向 01(R 约束/H 假设/§ 章节)、03(§ 章节)。

## 2. 十二个模糊问题簇

### A · 主线的形而上学——树的 HEAD 是什么

**直觉**:git 的力量一半来自 HEAD:你永远站在一个明确的"现在"。对话树没有 HEAD——你"站在"哪条分支上,只是"UI 最后打开的那条"。
**张力**:v6 说分叉结果是"线程列表里的**兄弟**条目"(平等);而 merge-back 的设想(H5"注回**源**线程")暗示主次。但"源"只是出生地,不是主权者——源线程可能早就死了。
**模糊问题**:
1. 当两条分支都活了很久,"主线"还有意义吗?"合并**回**主线"这个动词是不是从根上就错了——应该叫"汇流""广播""呈报"?
2. 树需不需要显式的注意力指针(HEAD)?由什么决定——最后打开?最后发言?用户手动?还是 DOI?
3. 若根本没有主线、只有"一个任务的多条平行人生",Q2 的全部语义要不要推倒重写?

### B · 恢复的颗粒度——回来的经济学

**直觉**:回来时,三句话会误导,三页等于没恢复。"最小充分集"存在吗?
**张力**:恢复笔记越准,越多人依赖;越依赖,一次误导的代价越大。R9 说不把沉默包装成安全——**但一段流畅的叙事本身就是一种被包装的确定性**(它比沉默更危险,因为没人怀疑它)。TF-0097 的 decided 拍只会说"在 X 处分叉出 2 条",说不出"因为"。
**模糊问题**:
1. 恢复信息的配比(你干了什么/世界变了什么/你为什么放弃)该由什么决定——离开时长?分支 DOI?还是干脆不配比,全部给出、让注意力自己挑?
2. "你不在时多了 N 条"是不是太粗?该不该是"多了 N 条,其中 M 条与你的前提冲突"(H2 的雏形)?
3. 用户该不该能在**离开时**给未来的自己留一句话?它是前置成本(违反 C1/R5)吗——还是离开时刻的自然动作,像下班锁门前看一眼办公室?

### C · 安静的悖论——被感知的保护

**直觉**:R7 要安静,R9 禁止把沉默包装成安全。但一个从不说话的哨兵会被当成不存在——**安全感的来源恰恰是知道它醒着**。
**张力**:tribunal 为 workspot 写者建了整套存在证明(5/15/30/50、洪泛闸、stats());chat 层连队列都没有(03 §9.5)。而且"没消息"永远无法区分"一切安好"和"它坏了"。
**模糊问题**:
1. 要不要"哨兵日志"式存在证明(本周封印 2 次、前提失效 12、洪泛 0)?它违反"无分歧不渲染"吗——还是说**系统自己的健康状态永远有资格说话**?
2. 可观测性(health)与告警(precision)是不是必须分离成两个通道?后者精度优先,前者不许沉默?
3. 建议式并发的信任是月抛型的:第一个月用户不信通知,第三个月开始依赖——"信任曲线"是设计空间还是想多了?

### D · 分叉的单位——一棵树还是两棵树

**直觉**:现在分叉的是**对话**(消息锚点),不是**代码**。用户迟早会问:"我分叉了对话,代码呢?"
**张力**:TF-0118 刻意把 chat 与工位分开("a thread is not a lane");R8 要求恢复对话/恢复代码是三个分开的动作(这是安全);但反过来"代码在 worktree 里分了叉、对话没分叉"的场面(workspot 上 agent 的对话属于哪条分支?)没有任何设计。
**模糊问题**:
1. "分叉对话不分叉代码"是 feature(轻、可逆)还是等待爆发的坑(血统说继承了一切,实际只继承了文本)?
2. 用户想要"分叉一切"时,树应该长在对话层、git 层,还是第三种"任务层"?legacy 的 workspace=工作树+会话 绑定被扔掉时,丢的是包袱还是本质?
3. 一条 chat 分支后来想领养一个 workspot(或反向),血统怎么过户?

### E · 理由的居所——推导的贫瘠与记录的暴政

**直觉**:"为什么放弃另一条路"是本项目最独特的主张,但理由不栖身于任何结构里。纯推导(账本纪律:完全从既有事实来)永远只能数出"分叉了 2 条",说不出"因为 A 依赖一个已废弃的 API"。
**张力**:让用户说,违反零记录负担与 v6 §8(不让人命名/分类);让机器猜,踩进"从散文推断结构"的坟场(90–99% 误报);**第三条路**:L3 的 N=2 重放——两条相似轨迹的差就是泛化,"把推断问题变成集合运算"。再压一层:Letta 74.0% 打败 Mem0 68.5%(01 §5)——**原始轨迹打败结构化抽取,"抽取销毁了信息"**。
**模糊问题**:
1. 理由有没有半强制的收集时机——分叉手势多按 300ms?分支收尾?还是永远不给,只靠 N=2 当场重算?
2. Letta/Mem0 证据是否意味着"理由库"这个念头本身该死——永远只留轨迹+指针?
3. 若理由只能"当场重建"而不能"预存",恢复笔记的 decided 拍还有存在意义吗?它的诚实形态是什么?

### F · drum 的 drum——人的 WIP

**直觉**:系统把复核者当鼓点(drum-buffer-rope),CONWIP 管 agent 派发。但没人管"你"——树的每条分支都在等你回来,**你的注意力才是全系统最后的瓶颈**。
**证据**:legacy 原话"agents are fast, you are the bottleneck";"the limit is your review bandwidth";wip.ts 只 gate dispatch,不 gate 人开新对话;FLOOD_LIMIT 注释承认人类容量 ~1 条/10 分钟(03 §1)。
**张力**:管人 = 家长式越权(厌恶清单第一条的变体);不管人 = 系统默许烂尾楼。unreviewedBacklog 已经是全局共享数字(TF-0084)——它现在只拦 agent。
**模糊问题**:
1. 系统该不该对你的第 5 条对话说"不"(不是技术不行,是你会把 5 条都变烂尾)?分叉手势要不要看 unreviewedBacklog——积压 >3 时软提醒"先复核再分"?
2. "岔开冲动"(v6 证伪线,每周计数)与"多车道冲动"是同一种冲动吗?该共享一个预算吗?
3. 有没有不越权的管理形态——比如只让"烂尾率"可见(每条分支挂着的天数),把判断留给人?

### G · 树的住址——CLI、GUI 与文件

**直觉**:树的数据活在文件里(meta.forkOf 可递归重建),但唯一能看见它的地方是 web GUI 侧栏的一个徽标。CLI 没有任何 tree/fork/thread 命令;chat 完全活在 HTTP 层(03 §4)。
**张力**:"文件即数据库"(local-first)意味着树天然跨工具、跨设备、跨 agent 可读——**但现状是只有 GUI 能读**。v3 说"Claude Code 卖引擎,Workbench 卖行驶记录仪",可记录仪的画面只有浏览器里能看。
**模糊问题**:
1. `workbench tree` 该不该存在(渲染血统的 CLI 命令——"对话的 git log")?它是树的正统住址还是第二个 UI 负担?
2. 树的"正确"呈现层是哪个:侧栏(现在)、专门的地图视图、还是 CLI?
3. 缺的到底是渲染器,还是事件流(H6:没有事件,任何视图都在事后考古)?

### H · 分支的结局——挂着的分支是负债还是资产

**直觉**:三分支结局(合并/留结论/放弃留痕)是设想;强制结局违反 R5。于是分支可以永远挂着——挂着的分支是"未完成的价值"还是"认知烂尾楼"?
**证据**:v6 §7"挂起的工作保持可见——仅仅看得见就是起作用的提醒";DOI 衰减天然提供"自然腐烂"模型;InkSync"验证界面胜过探索界面"。
**模糊问题**:
1. "放弃但留痕"应该是一个动作,还是 DOI 衰减到阈值的**自动归档**(留痕=状态变化,不是仪式)?
2. 归档的分支进入沉睡——它们该不该成为 DOI 检索的种子(某天新任务的足迹碰巧唤醒一条三个月前的分支)?这是 L1 的自然延伸还是复习式打扰?
3. 树的修剪由谁执行——人?DOI?还是永不修剪、只降权(树永远只长,只是有些部分褪色)?

### I · agent 的血统感知——Declaration 给谁看

**直觉**:ForkDeclaration 目前只返回给 UI("UI 负责呈现给用户")。但新 agent(freshAgentSession)对自己"从哪句话生出来、使命是什么"一无所知——它拿到消息前缀,却不知道那意味着什么。
**张力**:把血统注进 agent 上下文不算"用户画图"(contextgen 已经给 agent 发 .agent-context.md,03 §1),但它是"结构进对话"——踩在 R1/R2 的边界上。更深:血统感知会不会造成 agent 的**路线偏见**(盲目延续父对话的方向,恰恰毁掉分叉的意义)?
**模糊问题**:
1. ForkDeclaration 该不该成为新 agent 会话的首条上下文("你从对话 X 的这条消息分叉而来,继承 N 条消息,你的兄弟分支做了……")?
2. 兄弟分支的写集要不要进新会话的 contextNeeds(contextgen 现成机制)?这是 H1 的另一个实现位——比改 reconcile 循环更便宜?
3. "使命"是什么:推导标题?锚点消息?还是根本不给,让 agent 自己从继承的消息里读?

### J · 成功的行为信号——敢乱试

**直觉**:如果树成功了,用户会**变勇敢**:试错半径变大、敢弃置、敢复活、恢复靠系统不靠 git log。**恐惧消失是比效率提升更早出现的信号。**
**证据**:v6 整体证伪线(每周岔开冲动 <1 次 → L2/L3 不该建);C6"廉价的发散,只在回退可信时才廉价";InkSync:验证使被接受的错误编辑 −44%。
**模糊问题**:
1. "敢乱试"怎么测:分叉/回滚比?分叉后的发言变短变随意(=更信任)?reload 频率下降(被 fork 取代)?还是分叉与下一次发言的间隔变短?
2. 反向信号:什么行为说明树失败了?(分叉后从不回来 = 分支是一次性快照;恢复笔记确认率 ≈0 = 没人读;账本从不展开 = 安静失败)
3. 这些指标该不该进 events.jsonl 变成一等事件(H6),从而自动记账——还是一旦度量,古德哈特定律就进场?

### K · 元层自指——task-forest 是工具还是产品

**直觉**:workbench 管理 AI 辅助开发;而 workbench 自己的开发由 task-forest 管理(119 节点/39 提案/16 偏差)。这是自举,也是镜子:**森林的工程美德(会自纠虚报)与产品缺陷(fit:unknown 117/119)是同一套机制的两次成像**。
**模糊问题**:
1. fit 检查该由谁填——要不要在每个节点的验收里加一条"真实使用记录"字段?会不会把森林变成另一个自我打分循环(自己填 fit 给自己看)?
2. task-forest 该成为产品的一部分("你的开发也会长出森林")还是永远是内部脚手架?它 21MB 的嵌入全图事件流(01 §11)连自己都喂不动——先救自己还是先救用户?
3. 森林的事件流与 workbench 的 events.jsonl 要不要统一(K 与 H6 是同一个问题的两个角落)?

### L · chat/world 边界——TF-0118 是阶段还是永久

**直觉**:代码刻意把 chat 线程排除在车道体系外("a thread is not a lane")。这是当下的正确简化,但三支柱的全部合流点(分支作为写者 H1、merge-back 携带并发事实、恢复双通道 H2)**都要跨这条线**。
**模糊问题**:
1. 这条边界的正确终态是"两种公民,一个事件流"(统一 events.jsonl,不同 source)还是"两个国度,签证制"(翻译层)?
2. 统一后的**第一个新查询**是什么——"这个文件被哪些对话分支和哪些工位同时读过"?"哪些分支的前提被兄弟分支推翻了"?若一个都举不出,统一就是伪需求。
3. 边界消失后,tribunal 要不要收 chat 层告警(现在 chat 通知无队列无限速,而 fork 扇出会放大写者数)?

## 3. 从模糊到锋利:第二轮追加问题(建议并入 02 的派发,沿用同一四段格式)

### Q9 · merge-back 与"抽取销毁信息"的对抗

**为什么值得花 token**:merge-back(Q2)的最大理论敌人不在竞品,在自家证据:Letta 74.0% > Mem0 68.5%(01 §5)说明任何"摘要注入"都是销毁;但 C4 又说"人们很少回头"——纯指针永远无人点开。
**问题**:设计 merge-back 的信息形态谱系(纯指针/指针+一行摘要/摘要+溯源链接/完整轨迹追加),每级标注:信息损失率(定性)、被消费概率、"错了怎么办"的回退路径(v6 L3 条件 4:产物错了就回退到证据)。给出推荐形态与**信任模型**(用户何时开始信任回注物)。
**质量判断标准**:必须处理"摘要与轨迹冲突时以谁为准";不得引用没有证据的效率主张;答案必须兼容 R7(加法式)与"无分歧不渲染"。

### Q10 · chat/world 边界的终态(H6 × TF-0118)

**为什么值得花 token**:三支柱合流的每个具体方案(H1/H2/H5)都被这条隐形边界卡住;它是架构级决策,现在定比以后拆便宜。
**问题**:给出统一执行流的终态设计(或反证):事件 schema 如何同时容纳 workspot 足迹与 chat 足迹(后者已在记,03 §3);fork/leave/restore/merge-back 升格为一等事件后,列出**可执行的新查询清单**(跨对话与代码的),每条标注现有机制里它替代什么手工动作;明确什么**必须不统一**(TF-0118 的顾虑——"mix non-lane keys"——在统一后如何安置)。
**质量判断标准**:新查询至少 3 条且各自能表述为"省掉一次人的什么动作";迁移不引入数据库/重依赖(R11);对"agent 自称完成不可信"(R3)的影响必须讨论。

### Q11 · 人的 WIP 是否纳入 CONWIP(簇 F 的升级)

**为什么值得花 token**:drum-buffer-rope 的逻辑闭环要求瓶颈被 gate;人是最终瓶颈却不受任何 gate——要么论证"不该管",要么给出不越权的管法,这是产品价值观级决策。
**问题**:设计(或否决)"复核者 WIP"机制:unreviewedBacklog 已是全局数字;候选干预点(分叉手势、新线程创建、派发已有 gate);每个干预点标注家长式风险与最小干预形态(可见?软提醒?硬 gate?)。对照 tribunal 的 FLOOD_LIMIT(人类容量已被量化,03 §1)与 legacy 的"2-3 条实质任务"经验值。
**质量判断标准**:硬 gate 若被推荐,必须给出何时它退化为软提醒;必须回答"用户如何永久关闭它"(R7 对称退出);"不越权"的论证若成立,必须给出等价的自由放任方案及其可观测风险。
