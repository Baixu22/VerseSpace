# Fable 5.1 Briefing · Part 2 — 问题集(随 Part 1 一起喂;Part 1 做缓存前缀)

> 使用纪律:Part 1 是唯一事实来源,问题一律引用其编号(R=红线,H=假设,§=章节)。模型**没有**仓库访问权,凡答案依赖未给出的代码细节,应显式说"需要补充 X"而不是编造。
> 预算紧张时的最小派发:一次调用 = Part 1 + Q0 + Q1 + Q2 + Q6(攻击前提、统一抽象、merge-back 语义、失败模式——这四个决定其余一切)。Q3–Q5、Q7–Q8 适合第二轮带上下文追问。

## Q0 · 攻击前提(元问题,最先问)

**为什么值得花 token**:项目最大风险不是技术,是 117/119 节点 fit:unknown——整个体系没被真实使用检验过。让最强模型做一次系统性反方,比让它夸方案便宜得多。

**问题**:假设你是反方架构师。三支柱(交互/会话树/并发,§3)共同押注的根命题是:"单会话线性交互结构性地丢失试错历史与决策理由,且这个损失大到值得为其重建交互模型。"请:(a) 给出对这个根命题最强的三条反驳(包括但不限于:用户可能只想更好的线性恢复;fork 冲动可能天然 <1 次/周,触发 §7 整体证伪线;树的价值可能被 git + 会话摘要 90% 覆盖);(b) 对每条反驳,设计**成本最低、判决最快**的验证实验(≤1 周工程量,可复用现有 L2 部件);(c) 明确说出:哪些反驳若成立,三支柱中哪根该砍、哪些已建代码能无损保留。

**输出形态**:表格(反驳|成立时的迹象|判决实验|砍什么留什么)。
**质量判断标准**:反驳必须攻击根命题而非实现细节;实验必须能在两周内出数;"砍什么留什么"必须具体到 §3 的已建部件。

## Q1 · 统一抽象:三支柱是一层还是三视图?

**为什么值得花 token**:三支柱目前是三个子系统、三条独立事件流(§2 断层)。若存在统一原语,后续每个功能都便宜一个数量级;若不可统一,需要它的形式化理由来阻止未来的伪统一。

**问题**:已知系统底座是 append-only 事件日志 + 派生投影(ADR-0008:结构来自执行;R3:单调性)。交互(DOI 显著性排序)、树(决策拓扑:fork/variant/merge)、并发(前提失效:读集 vs 世界)是否可被建模为**同一条执行流上的三个投影**?若可以:给出统一事件原语的最小 schema(字段、不变量、单调性分类——每字段过 ADR-0007 的"后到事实会推翻它吗"判据),并说明 fork/leave/restore/merge-back 如何成为一等事件、现有三条流如何无损迁移。若不可以:给出精确的不可统一定理式论证(哪两个投影的需求在什么不变量上冲突)。

**输出形态**:schema 草案 + 不变量清单 + 迁移路径;或反证论证。
**质量判断标准**:每个字段标注单调/非单调;schema 能同时表达 §3 中全部已建行为且不要求改动 R4(建议式)与 R7(加法式);迁移路径不得引入数据库或重依赖(R11)。

## Q2 · merge-back 的最小正确语义(树线最大缺口)

**为什么值得花 token**:merge-back 是竞品确认的空白(issue #32631),也是树从"记录"变成"资产"的关键一步;语义选错会污染主线,不可逆地毁掉信任。

**问题**:在 R5(无提议 UI,直接做+廉价撤销)、R7(加法式)、R8(三个恢复动作分开)、R12(拆除 ≤ undo)约束下,设计 merge-back:(a) 给出**语义三级**(引用指针/摘要注入/内容合并)各自的失败模式、适用判定条件、与 merge-guard 和接口注册表(§3 并发行)的交互——尤其:分支碰过代码时,回注应该携带什么并发层事实?(b) 回注物在源线程里以什么形态出现才不违反 R7(一条系统消息?一个折叠卡?)?(c) 与 H5 对比:它缺了什么、多了什么?(d) 给出验收标准(可用 §7 风格:用户不看代码能否理解"这条分支给主线留下了什么")。

**输出形态**:语义矩阵(级别×失败模式×判定条件×undo 方式)+ 一个端到端用户故事(从 fork 到 merge-back 的完整交互序列)。
**质量判断标准**:失败模式必须包含"回注后源线程上下文被稀释导致主线质量下降"这类第二阶效应;方案不得引入任何确认对话框(R5);必须说清与已建的 `meta.forkOf`/决策账本/恢复笔记的数据关系。

## Q3 · 分支作为写者:把 R2 从"写者间"扩展到"分支间"

**为什么值得花 token**:这是并发与树的真实交点(H1),也可能整个三支柱统一框架的最小可行切片——它同时让 merge-back(→Q2)与恢复(→Q4)获得并发层事实。

**问题**:现状:fork 的新线程 `freshAgentSession`,无读集;兄弟分支 A 写盘后,B 的继承前提静默失效(§8 会话树行)。请设计:(a) H1 方案(分叉时从继承前缀足迹合成初始读集,复用现有 reconcile)的正确性边界——什么情况下合成读集会**漏报**或**误报**?足迹里哪些信息(used/generated/64KB 暂存)该进、哪些不该?(b) 分叉事件是否应携带 touch-scope(从足迹推导,零用户输入)以化解 C1 摊销矛盾(H4)?给出摊销算术:fork 频率 vs 声明成本 vs 冲突预警收益,用 §5 数据估计量级。(c) 这个机制对 merge-back 的裁决提供什么?(d) 列出此机制与 R9(精度优先)的张力:分支间误报的下游自纠路径存在吗?

**输出形态**:机制草图(数据流级)+ 失效模式表 + 摊销算术。
**质量判断标准**:必须复用现有 premises/delivery/footprint 部件而不是新建子系统;必须回答"为什么这不是编排器"(R10);摊销算术必须区分"每会话"(C1 禁止)与"每分叉事件"(低频可摊)。

## Q4 · 恢复的双通道:叙事 + 仓库事实如何合成一个"回来时的处境"

**为什么值得花 token**:这是三支柱中唯一直击"最贵痛点"(回来时想不起来)的合成点;TF-0097 已建叙事半边,缺事实半边,合成设计决定它是否真的省心。

**问题**:现有恢复笔记是纯函数启发式(§3),不含"为什么放弃另一条";R2′(恢复时 diff 读集,注入"37 个前提 4 个为假")未建。设计:(a) 双通道信息架构:节拍(叙事)与前提漂移(事实)的排列、优先级、折叠层级——遵守 R7 与"无分歧不可见";(b) **冲突语义**:叙事说"动了 X"但仓库显示 X 已被回滚/被第三方改写——呈现规则是什么?哪边赢?(c) 现有 beats 里"decided"拍升级路径:决策账本(分叉/备选计数)何时值得被替换为真正的理由记录?在不增加用户记录负担(账本纪律:完全从既有事实推导)的前提下,理由的最大信息源是什么?(d) 给出与 TF-0097 验收句("隔天恢复无需翻 git log")兼容的验收升级。

**输出形态**:恢复卡的线框级信息架构(ASCII)+ 冲突规则表 + 验收句。
**质量判断标准**:零新仪式(无必填输入);冲突规则必须可被测试表达;必须处理"离开很久且仓库大变"的退化情形。

## Q5 · 隐式→显式的升级判据与树的清理学

**为什么值得花 token**:树会长熵;没有清理学,分叉越有用,列表越快变成沼泽。L3(N=2/重放)整体未动,需要判据而不是里程碑。

**问题**:ADR-0008 的杀死判据("若一个衍生产物无法通过执行来检查,且其输出空间开放——不要建它")之下:(a) Mylyn DOI 的信号面(selection/edit)在 chat 语料上的重定义:候选信号(线程切换、消息引用、fork 子嗣活跃度、恢复笔记被确认/编辑、merge-back 被撤销)各自的可执行性(能否从执行轨迹测得)与噪声水平;(b) 基于 DOI 的树清理学(降权/归档,可逆)是否通过杀死判据?给出 DOI 衰减模型的形式化起点(半衰期?访问计数?)与它必须满足的 R7 约束;(c) L3 的 N=2 推导判据:什么信号累积到什么阈值,才值得把一个隐式衍生物升为显式占位符?对照 L3 验收(重放 diff + 拒绝占位符无需审计全产物)。

**输出形态**:信号×可执行性×噪声表 + 衰减模型草案 + L3 升级判据。
**质量判断标准**:每个信号标注采集点(现有足迹/交互日志/需新增);衰减模型不得要求用户任何输入;明确说出哪些信号在现有事件流里不存在(呼应 H6)。

## Q6 · 失败模式审计:"看起来很美但会崩"清单

**为什么值得花 token**:体系越自洽,单一叙事的盲区越致命;这是付费模型性价比最高的一类问题。

**问题**:对三支柱组合(安静交互 + 持久决策树 + 建议式并发),给出**至少六种**失败模式,必须覆盖:(1) 恢复笔记过时/幻觉误导(叙事与仓库漂移);(2) 树熵(分支无限增长);(3) 通知洪泛(注意:fork 扇出会放大写者数,而 chat 层通知无队列限速,tribunal 只管 workspot——§8);(4) 沉默伪装安全(R9 红线的反面:精度优先导致用户过度信任"没消息=没问题");(5) merge-back 污染主线(第二阶:主线上下文稀释);(6) METR 陷阱(恢复/账本界面增加阅读时间,验证成本对用户不可见——用户无法报告它在失败)。每个给出:早期检测信号(可观测的量)、熔断设计(与 R12 廉价可逆兼容)、以及它最可能先在哪种用户画像上出现。

**输出形态**:六行以上的失败矩阵(失败模式|检测信号|熔断|首现画像)。
**质量判断标准**:检测信号必须是现有系统已经记录或一行代码可记录的量;熔断必须是关掉一个开关而非回滚架构;至少一条失败模式必须是我没列出来的。

## Q7 · fit 优先的验证路线图(把"用没用"焊进流程)

**为什么值得花 token**:117/119 fit:unknown 是元风险;需要的不是更多功能,是把 §7 证伪纪律变成可执行排期。

**问题**:假设约束:单人项目,每周 ≤4 小时工程 + 日常真实使用;已有 L2 全部部件(§3)。设计 12 周计划:(a) 每周一个最小可验证假设(从 H1–H6 与 §8 开放问题中选),验收方式为真实使用记录而非测试通过;(b) 每个假设给出:工程量估计、记录什么数据、判据、go/no-go 门(引用 §7 的 <1 次/周证伪线);(c) 给出决策树:若 Q0 的某反驳成立,计划如何收缩;(d) 明确哪些 proposed 节点(TF-0099/0100/0101/0085)应该被推迟或杀死。

**输出形态**:12 周甘特式表 + 决策树。
**质量判断标准**:每周产出必须是"用户行为数据"而不是"功能上线";总工程量 ≤48 小时;至少三周的假设是关于"砍"而不是"建"。

## Q8 · 命名与哲学框架(Phase 2 的升华题,最后问)

**为什么值得花 token**:当前对外描述("交互+会话树+并发")是工程分类,不是理念。一个准确的命名能同时约束未来功能边界(防止为做而做)和对外定位。

**问题**:把这套东西升华为一个可命名的理念框架。已知素材:时间分叉 vs 空间复制(Nimbalyst 对照)、"对话是输入面,执行是结构的来源,仓库是结构的裁判"、"注意力/前提维护问题而非编排问题"、树是"决策的证据"而非"窗口的排列"。给出 3–5 个候选框架,每个:名字(中英)、一句话公理、它自然推出什么功能、它**禁止**什么功能、它最容易滑向的堕落版本。最后:如果只能保留一个框架,选哪个,为什么其余该死。

**输出形态**:框架矩阵(名字|公理|推出|禁止|堕落版)。
**质量判断标准**:公理必须能推导出 R1–R12 的大部分红线(即红线是公理的推论而非并列清单);堕落版本必须是真实可想象的 产品演化路径,不是稻草人。
