## 0. 一段话总结

VerseSpace 以 Helmor 桌面应用代码库为冻结基线起步，在 `packages/workbench` 从零建成了一套「CLI + 文件系统状态管理器」运行时（七模块，115 测试，本机 win32 全绿），并已完成两个 GitHub Release（四平台单文件二进制）。产品定位经过三次收敛（v1 任务胜过会话 → v2 两态模型 → **v3 任务主权层**），当前形态是：**对话式交互（assistant-ui 前端）+ 深度定制的 runtime 并发层 + 任务身份证治理模型**。前端 MVP 已可日常使用；「会话挂靠任务」是下一个决定性功能，尚未开工。

---

## 1. 项目定位演进（为什么是现在这个形态）

| 版本 | 命题 | 结局 |
| --- | --- | --- |
| 定位 v1 | 「任务制赢过会话制」 | 被用户与自查驳回：总成本账只算监督税、忽略设计时税；为 5% 场景设计却声称普适 |
| 定位 v2 | 「两态模型：探索归对话、履约归契约」 | 半修正：承认了对话的优势，但「探索态界面归别的工具」仍不对 |
| **定位 v3（现行）** | **任务主权层：对话即引擎，任务即身份证，治理即副产品** | 载入 `docs/positioning.md`（`c4f886b`） |

v3 三句话：① 每个任务一张身份证（ID、元数据、履历、场所）；② 会话挂靠任务之下（会话无主流离是治理失效的根源）；③ 治理是运行时副产品（git diff / transcript / 验证结果自动上卡），不由用户前置填写。

交互层结论（经实证与两轮反驳收敛）：**对话式 agent 不可推翻也不需要推翻**；Dify/Coze 式手动工作流 DAG 与纯工作台均被明确排除；不做 a2a/multi-agent 协议。产品的全部深度在 runtime 层。

相关决策记录：`docs/decisions/0001-0005`（运行时 Bun、包落位、Helmor 冻结、基座自研+借库、本地 Web GUI）。

### 3.2 MVP 闭环（已达成并端到端验证）

`init → goal（依赖）→ ws create → dispatch（真实 git worktree）→ checkpoint 落 staging → sync（Verifier 真跑）→ verified→applied → goal done → 工位释放+上下文刷新 → 接口漂移 → stale 传播 → 稳态零转移`。真实 git 仓库夹具，通过/失败两分支均验证。

### 3.3 对话运行时（`src/chat/threads.ts`，本轮重心）

- 线程存储：`.workbench/threads/<id>/`（meta.json + messages.jsonl）——文件即状态，崩溃可恢复。
- **提供商（4 个，全部真实流式）**：`claude`（本机 CLI stream-json + `--resume` 续聊 + plan/acceptEdits 权限模式）/ `openai-chat`（Chat Completions SSE）/ `openai-responses`（Responses 流式 + reasoning effort）/ `anthropic`（Messages SSE）。统一 SSE→delta 事件管线；API Key 存本地 workbench.yaml，接口永不下发明文。
- 并发模型（产品核心）：线程内串行（单 in-flight run），**线程间真并行**（独立子进程/fetch）；取消 = 杀子进程或 abort fetch，状态不丢。
- 消息模型：**parts**（text / tool-call 含 result 回填）；plan 模式（--permission-mode plan → 批准卡 → acceptEdits 恢复执行 → 自动回落）。
- 事件流：user/delta/tool/tool_result/done/error，全量 NDJSON。

### 3.4 实证记录（对真实 claude CLI 2.1.220 的探测，决定过设计）

1. 无头模式 **AskUserQuestion 工具不存在**（模型明确拒绝）→ 结构化人机决策走 plan 批准卡。
2. **ExitPlanMode 不可靠**（plan 模式以纯文本输出计划即结束）→ plan 模式做成 runtime 机制而非依赖工具发射。
3. **本环境无头工具执行被禁**（默认/allowedTools/bypass 三种方式均预拒）→ tool-call 渲染已就绪但点亮依赖宿主环境配置。
4. Windows cmd stdin 竞态：立即写 prompt 会被吞 → 首个输出块后发送（500ms 兜底）。

### 3.5 测试与质量

115 测试（27 文件）全绿于 win32：七模块单测、真实 git 仓库 MVP 端到端、容错与并发写入组、chat 线程运行时（含假 agent 流式）、UI server、verifier（含真实超时击杀）。关键修复史均有测试背书：verifiedAgainst 锚定缺失（e2e 抓出）、commander 零/单操作数传参崩溃（二进制验收抓出）、队列残留（doctor 抓出 → dequeue_goal 转移）。

## 5. 交互策略（当前定调）

三定律（编码于 UI 与提交历史）：

1. **裁决优先**：首屏第一公民是「需要人拍板的事」；无例外时首屏塌缩为一行空态——信息税的下降来自「只看例外」。
2. **跑道即并发**：N 个 worktree 的并行是一屏跑道，不是标签页横跳。
3. **对话是证据，不是骨架**：对话流内嵌于任务、默认折叠、可回放。

定位文档（v3）同时记录了诚实边界：契约制有设计时税，对「问一句→看结果→微调」型交互对话完胜；**渐进披露**——默认用户只需三个概念（task/workspot/checkpoint），DAG/接口锚定/状态机是系统内部机制。

## 7. 阶段展望（R1–R4）

### R1 任务身份层（下一个功能，未开工）

- **目标**：让会话出生就在任务之下——落实定位 v3 的「会话挂靠 + 身份证自动生长」。
- **内容**：`workbench task new <title>` 创建任务身份证（含自动生成的任务目录）；`workbench task talk <id>` 在任务上下文包裹对话（CLI 或前端面板），transcript 落盘任务目录；**元数据自动上卡**：git diff 捕获（动过的文件）、命令历史（transcript 解析）、验证结果、决定抽取；前端任务卡列表成为首屏（渐进披露：不建任务时等于普通对话）。
- **验收**：一段对话结束后，任务卡上无需任何手动操作即可看到「动过的文件/跑过的命令/已验证状态」。
- **依赖**：现有 chat runtime（✅）、events（✅）、watcher（可复用捕获）。
- **风险**：transcript 解析对 CLI 版本敏感；元数据抽取的信噪比。

### R2 并发治理深化（并行跑道的任务化）

- **目标**：把「线程并行」升级为「任务内多会话并行」——多 agent 在同一任务的多段会话/多个 workspot 上工作，塔台信息回到任务卡。
- **内容**：任务 ↔ 多会话 ↔ 多工位的归属模型；会话级状态（running/done/failed）聚合到任务卡；裁决队列以卡片区块回归（待审 checkpoint/失败验证/冲突）；每任务的上下文预算视图。
- **验收**：3+ 并行任务的人工监督不需要切换终端；裁决都在一个界面完成。
- **依赖**：R1 的身份证模型；scheduler（✅ 已支持并发上限）。

### R3 契约自动结晶

- **目标**：checkpoint 不再要求用户手动落——从对话与验证结果自动生成草稿（草案仍需裁决，保持「完成由机器裁决」不变）。
- **内容**：任务 talk 中检测「用户验收意图」→ 自动起草 checkpoint（assertion 从验收条件与对话提炼）→ plan 批准后自动开工位 → 完成后 Verifier 自动跑。
- **验收**：R1 的动线上，用户全程没有手动写过 YAML，但 .workbench 里形成了完整的可审计契约。
- **风险**：自动起草的质量——保持 human-review 兜底。

### R4 发行与规模化

- **目标**：v0.4 → v1.0 的工程化收尾。
- **内容**：Actions 计费恢复后验证/重写 CI 与 release workflow（现车道已接线未在线验证）；npm 公开发布（包形态已备）；macos/linux 二进制宿主冒烟；多项目/多工作区支持（一个 runtime 管多个 .workbench/）；Helmor 存量退役评估（TF-0055）。
- **验收**：真机三平台安装冒烟；CI 全绿含 workbench 车道；文档齐备到新人可按 README 复现。

### 明确不做（持续有效）

a2a/multi-agent 互聊协议 · 手动工作流 DAG 编辑器 · 取代对话的通用工作台 · 数据库/服务器依赖 · Agent SDK 内嵌（保持 agent 无关）。
