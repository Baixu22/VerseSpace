# ADR-0007：单调优先 —— 与其协调，不如把操作改造成不需要协调

- 状态：提案（待用户裁决）
- 日期：2026-08-30
- 相关：[`positioning-v5.md`](../positioning-v5.md) §5 · ADR-0006（建议式并发控制）

## 背景

ADR-0006 决定了"免不掉协调时怎么办"（建议式通知 + 选择性修补）。本 ADR 处理它上游的问题：**哪些操作根本不需要协调，以及如何把需要协调的操作改造成不需要。**

**CALM 定理**（Hellerstein & Alvaro, CACM 63(9) 2020；形式化证明见 Ameloot et al. 关系传感器）：

> 一个程序存在一致的、无协调的分布式实现，**当且仅当它是单调的**。

其中"一致"指**汇流性（confluence）**——程序的*结果*在输入的任意顺序与批次下确定，**不是线性一致性**。单调性定义：对输入集合 *S ⊆ T*，有 *P(S) ⊆ P(T)*。

**一行判据：后到的事实会不会让这个结论变错？**

正典对照说明了判据的锐度：分布式**死锁检测**（环*存在*——新边只会增加环 → 单调 → 免协调）对比分布式**垃圾回收**（路径*不存在*——后到的一条边就推翻结论 → 必须"知道自己听全了" → 必须协调）。**同一个图可达性问题，"存在 vs 不存在"就是全部差别。**

可操作化：Bloom 把单调性变成**语法可判定**的——并集、连接、投影、选择单调；**差集、反连接、否定、聚合**是被标记的非单调算子，每一处出现都是一个必须插入协调的"points of order"。（注意：**裸赋值是非单调的**——它意味着收回，这也是为什么这套分析不能直接用在命令式代码上。）

**I-confluence**（Bailis et al., VLDB 2015）是其操作版本，且更适合我们：它是**（不变量，操作）这一对**的性质，不是操作单独的性质。经验数据：TPC-C 的 12 条不变量里有 10 条是 I-confluent。可判定性上，**不变量闭包是充分但不必要条件**；Whittaker & Hellerstein 的 `Lucy` 是**交互式**过程，需要开发者提供不可达性——**不存在按钮式自动判定**。

成本背景（Saito & Shapiro 六轴分类）：我们选的是**多主 + 操作传输 + 语义调度 + 语义解决器**——**每一轴上最贵的角**。Gray et al.（SIGMOD 1996）：朴素多主的并发更新率随主节点数 **O(M²)** 增长，**节点与流量各增十倍则死锁/调和增加一千倍**。该综述的处方（快传播、切小对象、**对象内优先单调结构**）正是本 ADR 的方向。

## 决策

**在设计任何 agent 可执行的操作时，先问它是否单调；若非单调，优先改造而不是协调。**

### 1. 分类表（写入实现，作为操作注册时的必填元数据）

| 操作 | 支配不变量 | 单调 | 处置 |
|---|---|---|---|
| 追加文件 | 只增序列 | ✅ | 免协调 |
| 新增文件 / 模块 | — | ✅ | 免协调 |
| 加 import / 引用已存在符号 | 外键 + Insert | ✅ | 免协调 |
| 在**新命名空间**建符号 | 唯一性，"选某个值" | ✅ | 免协调 |
| 在**指定名字**建符号 | 唯一性，"选特定值" | ❌ | 协调，或分割命名空间 |
| **删除符号** | 外键 + Delete | ❌ | 级联删除；或**墓碑 + 后台 GC** |
| **重命名** | = 删 ∘ 建 | ❌ | **加别名 → 迁移 → 事后移除** |
| **改签名** | "每个调用点类型检查通过"（NOT-EXISTS） | ❌ | **加重载 → 迁移 → 事后移除** |
| **断言"测试通过"** | "不存在失败的测试" | ❌ GC 那一类 | 对被测区域**封印** |
| **标记完成 / "构建绿"** | 全局 NOT-EXISTS / COUNT | ❌ | **封印** |
| 自增 id（迁移序号、端口） | AUTO_INCREMENT + Insert | ❌ | 协调或托管区间 |
| **记录一次读（前提）** | — | ✅ | 免费——**产生失效通知的来源** |
| 有下界的预算消耗 | `> Decrement` | ❌ | 托管 |
| 有上界的计数增加 | `> Increment` | ✅ | 免协调 |
| "符号 X 存在" / "文件含 S" | CONTAINS | ✅ | 免协调 |

### 2. 三条逃生路（按优先级，先试上面的）

- **(a) 改造成单调** —— 墓碑、别名、先加后迁。**把协调移出关键路径**（Dynamo 式）。「重命名」→「加别名 → 迁移 → 移除」把一个必须协调的操作换成三个免协调的操作。**这比任何协调机制都便宜。**
- **(b) 封印分段（sealing）** —— 路径 glob / 模块 / 符号集上的租约。分段内免协调，只在跨段时协调。Blazes 的 punctuation（"此分段已停止变化"）用点对点通知替代全局屏障，报出至多 **3×** 吞吐。分段不变量汇流性实测：**跨段罕见时 10–100× 于线性一致复制；跨段频繁时反而输**。**注意：作者自陈找到有效分段"可能是个繁重的过程"，不可自动化——不要试图自动推导分段。**
- **(c) 事后补偿** —— saga 逆操作（ADR-0006 §1.5）。

### 3. 直接的工程后果

- **任务分解时优先产出单调操作。** 这与 §9 的"杠杆在上游"一致：与其改进合并算法，不如让 agent 产出的变更本身就可交换。
- **"完成"与"构建绿"是非单调的**，因此它们**必须**由 Verifier 在一个被封印的区域上裁决——这解释了为什么现有 Verifier 架构是对的，也解释了为什么"agent 自称完成"永远不可信。
- **`events.jsonl` 的只增日志是唯一真正需要的 CRDT**（G-Set，并集合并）；对象内其余状态优先选择单调结构（只增日志、只并集合、单调递增计数器）。
- **`interfaces.version` 单调递增**是 ADR-0006 继承的不变量之一，与本 ADR 一致。

## 后果

**正面**

- 提供了一个**判据**而非直觉，用于回答"这个操作要不要走协调路径"，可写入代码作为操作元数据。
- 把最贵的一层（协调）的工作量系统性地转移到最便宜的一层（设计），符合 positioning-v5 §1 的三层阶梯。
- 与"产品必须可证明地不是编排器"一致：单调操作**天然不需要任何编排**。

**负面 / 风险**

- **没有自动判定。** 分类必须人工完成并随新操作维护；`Lucy` 类工具是交互式的。分类表本身可能出错，需要在 ADR 中随实践修订。
- **改造有成本。** "加别名 → 迁移 → 移除"是三步而非一步，且中间态会在仓库里停留一段时间。对小改动可能不划算——**应设一个门槛：只对跨越多个写者可见范围的操作强制改造。**
- **封印分段不可自动化**，且跨段频繁时反而比线性一致更差——**引入分段前必须先测量跨段频率**。
- 本 ADR 的分类基于对 Bailis 证明编号的映射，属**转写而非原始证明**；边界情况（例如"改签名"是否总能归约到 NOT-EXISTS）需要在实现时逐条复核。
