# ADR-0028：延续性接入既有表面（恢复卡、MCP、面板）

- 状态：已接受（2026-11-01）
- 补充 ADR-0027（会话延续性作为第四个投影）；ADR-0023 的功能冻结只在本文件声明的纵切片内放开；ADR-0024 的退役范围不变。
- 追踪：任务森林 TF-0321 / TF-0322 / TF-0323 / TF-0324 / TF-0325 / TF-0326 / TF-0327 / TF-0328（本机 untracked 脚手架）。

## 问题

ADR-0027 把「这一轮被切断」变成账本里的观察，并给了 `workbench sessions continuity` 一个 CLI 面。但那时它只住在 CLI 里：模型在回合中问不到它，人在面板的恢复卡上看不到它。ADR-0027 §「边界」明确写了「不接 MCP 与面板——接它需要新的表面测试与一次产品读数」。

这一轮补的就是那一步。补之前有两个具体风险，不是「多接一个界面」那么简单：

1. **同一个事实三种读法。** 延续性已经由 CLI 输出，若 MCP 与恢复卡各自再算一遍，三处必然漂移——这正是本仓既有纪律（ADR-0010「一条日志、两类事实、三个投影」、ADR-0026 的同一纪律）要防的。
2. **红点墙。** 真实账本上 30 条会话里有 20 条带未投递积压。若积压被读成「待办」，恢复卡会退化成一片提示，真正的断点反而看不见。ADR-0027 把积压单列成一维，本决定要保证这条在**面板上**也成立。

## 决定

### 1. 三处表面读同一份投影，不各算一份

`chat/continuity` 保持唯一推导层（纯函数 `derive.ts` + 只读 `read.ts`）。CLI、MCP `continuity`、恢复卡与 `/api/chat/threads/<id>` 的 `continuityDelivery` 全部走它。恢复卡只做「哪些行要出现在卡片上」的取舍（下面的判据），不重新判定 state。

聊天 GET 一次请求里只读一遍事件日志：`readSessionContinuity` 接受调用方已经读到的 `{ events, pending }`，否则同一份账本会被读两遍，两份读法分叉时卡片与读数会互相矛盾。

### 2. 恢复卡的行判据（TF-0323，先于实现落地）

判据写成可执行的 `chat/resume-card/continuity.ts`，由卡片测试直接引用，不只在文档里另说一遍：

| 观察 | 卡片行为 |
| --- | --- |
| `intact`（含已恢复的中断） | **不产生任何行**。健康不占空间：卡片不因为「检查过」而多一块。 |
| `review`，有一条未恢复的中断 | **恰好一行**，排事实区最前，`refs` 逐条为 `event:<id>`，可在证据接口打开。 |
| `review`，中断之后已有助手消息 | 该中断**不进卡片**。记录留在账本里，不再占注意力。 |
| 有未投递积压 | **不变成事实行**，只作卡片头部一个计数（`~ N 个文件待通知`），与 CLI 的 `~` 同一维度。 |
| `unknown`（材料不足） | **不产生行**。材料缺口由 CLI 与 MCP 报告；卡片只在有具体待办事实时说话。 |
| 同一条会话既有断点又有积压 | 断点行先、且钉在预览之外；积压留在头部。文件事实照旧按 `factsPreviewCount` 折叠。 |

`pinnedFacts` 是这份判据的载体：服务端告诉客户端「前 N 行不许折叠」，客户端不自己猜哪一行重要。

**卡片上不做的事**（与 ADR-0027 一致，写进判据不是遗漏）：不重跑那一轮、不重投通知、不归档线程、不把 `review` 变成任何动作。这一行只是「有一条没被回答的中断」这个事实。

### 3. MCP 第六个工具 `continuity`（TF-0326 / TF-0327）

- **契约是读数的子集**：三态 `state`、`identity`、`turns.interruptions`、`delivery` 与 `refs`。不引入新判据，不新算概率或分数。
- **只读**：实现里没有任何写调用；表面测试断言「调用前后账本事件数不变」。
- **体积**：整段过 `truncate`（默认 ≤2000 字符，超出标注剩余字符）。
- **0 / 1 / 多条线程三种形态都正确**；线程不存在时返回可读错误文本，不让 JSON-RPC 变成崩溃。
- 工具目录模块化：`mcp/tools.ts`（298 行）拆成 `mcp/tools/`（每工具一文件 + `types.ts` + `index.ts`）。名字、描述、schema、体积预算只在一处出现。

### 4. 表面漂移测试（TF-0328）

新增 `mcp/tools/surface.test.ts`：断言目录恰 6 条、顺序由 `MCP_TOOL_NAMES` 单一来源决定、每条描述含「只读」、每条在空账本上可调用且不写账本。另有 `artifacts/projection.test.ts` 里一份**刻意硬编码**的第二读法——两处都红才叫「三处一致」。

### 5. 展示观测扩展到通用行标签（TF-0325）

`thread.resume_card_shown` 原来只记 `branchRows`。现在同一条事件增加 `rows`（通用行标签：`branch:<threadId>` / `interruption:<eventId>`），`branchRows` 保留为**由 `rows` 派生的只读视图**，旧折叠器（`branch-engagement`）与旧事件照常可读。这不是两套记录，是同一条观察的兼容扩展；旧客户端仍可只发 `branchRows`。

## 边界：本切片不做什么

- **不新增判据。** 三态与「中断后有无助手回复」仍是 ADR-0027 那一条，本切片只把它搬到两个表面。
- **不做自动动作。** 没有重跑、重投、归档、修复；`review` 不触发任何调用。
- **不把积压并入 state。** 实测 30 条会话里 20 条带积压，并入会淹掉真正的断点。
- **不引入授权/派工概念**（TF-0332 的载体）：没有 Mandate / Ticket / Assignment。
- **不声称会话正确。** `intact` 只说明没有观察到需要人处理的事实。
- **不恢复非 Windows 实机或真人研究**（ADR-0024 不变）；本切片的读数是 Windows 本机工程读数。
- **不改 `reload` / `fork` / 跨 provider 语义。**
